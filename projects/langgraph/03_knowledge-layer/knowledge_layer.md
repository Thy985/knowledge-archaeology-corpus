# 03 Knowledge Layer — LangGraph（8 KO，含聚合规则）

> 每个 KO 声明 aggregation_rule（R1 机制簇 / R2 因果链簇 / R3 不变量簇 / R4 主题簇）+ 簇内 EK + 解释范围扩大论证。聚合理由禁止"都属于某子系统"。

## KO-01 图执行引擎 = 版本化状态机（R4 主题簇）
- **声明**：把并发、持久化、触发调度统一折叠进"版本化状态机"：状态=通道值，转换=节点写，触发=版本推进，快照=checkpoint。Agent 编排因此获得确定性、可恢复性、可调试性三个属性。
- **簇内 EK**：EK-01（超步循环）/ EK-02（确定性写应用）/ EK-03（版本计数）/ EK-14（versions_seen 触发）/ EK-15（恢复）/ EK-31（读取）/ EK-32（写入）
- **边类型**：mechanism（01↔02↔03 共享超步/版本机制）+ causal（03→14→01）
- **解释范围扩大**：从"langgraph 怎么跑"扩展到"任何图执行引擎（workflow 引擎/状态机框架）可借鉴的设计"
- **反例**：DAG 静态执行器无版本（一次拓扑排序跑完）；纯函数式数据流无状态快照
- 层级：L4 Cognitive Model；证据强度 S4（测试验证）

## KO-02 状态契约全链路：编译期→运行期（R2 因果链簇）
- **声明**：框架把"状态正确性"前置到编译期：schema→通道推导→reserved 校验→订阅校验→serde 白名单，运行期引擎才被允许"信任"状态不变量。编译期犯的错在编译期死，运行期只处理执行错误。
- **簇内 EK**：EK-16（compile 流水线）→ EK-17（通道推导）→ EK-08（reserved 校验）→ EK-09（订阅校验）→ EK-11（checkpoint 结构）→ EK-12（saver 契约）
- **边类型**：causal 链（16→08/09/37→17）+ dependency（12→11）
- **解释范围扩大**：从 langgraph 编译流程扩展到"类型安全框架的编译期契约设计"
- **反例**：动态语言框架（无 schema 校验）把错误推迟到运行期
- 层级：L3 Pattern；证据强度 S4

## KO-03 interrupt/HITL 生命周期协议（R2 因果链簇）
- **声明**：人机交互不是"暂停点"而是"可恢复的异常事件"：挂起（异常）→持久化（checkpoint）→客户端决策 →恢复（重执行）→resume 匹配。interrupt 把 HITL 变成状态机的合法转换，而非旁路。
- **簇内 EK**：EK-20（挂起）→ EK-21（恢复重执行）→ EK-22（Command）→ EK-23（映射）→ EK-24（编译期配置）→ EK-25（answered 跟踪）
- **边类型**：causal 链（20→21→22→23）+ dependency（20→12）
- **解释范围扩大**：扩展到任何需要人机协作的 agent/工作流框架（审批流、人工确认、工具授权）
- **反例**：同步阻塞式 HITL（wait_for_input）——无法持久化/无法并发/无法重放
- 层级：L4 Cognitive Model；证据强度 S4（test_interruption.py 族）

## KO-04 版本不变量：无锁并发的正确性基础（R3 不变量簇）
- **声明**：并发节点不需要锁，因为三条不变量成立：①通道版本单调递增 ②节点只被"其未见版本推进"触发 ③写应用顺序确定。任何破坏这三条的操作（乱序写、版本回退、未记账触发）都会导致状态错乱。
- **簇内 EK**：EK-03（版本计数）/ EK-04（单值约束）/ EK-14（versions_seen）/ EK-33（读取语义）/ EK-35（未知通道宽容）
- **边类型**：constraint（03/04/14 汇聚到同一正确性不变量）
- **解释范围扩大**：扩展到分布式状态机/乐观并发系统（CRDT、多副本日志）
- **反例**：非确定性任务排序（无 path 排序）；版本用 wall-clock（非单调）
- 层级：L4 Cognitive Model；证据强度 S5（修复史 #9142/#9165/#9170 印证其脆弱性）

## KO-05 记忆分层：短时/长时/增量（R4 主题簇）
- **声明**：框架记忆分三层：线程 checkpoint（短时、完整、每超步）、增量 delta（压缩路径）、store（长时、跨线程、语义寻址）。三层记忆服务于不同时间尺度，不可互相替代。
- **簇内 EK**：EK-07（delta）/ EK-11（checkpoint 结构）/ EK-12（saver）/ EK-39（store）/ EK-40（conformance）/ EK-47（delta 测试族）
- **边类型**：subsystem（记忆子系统族）+ contrast（11 vs 39）
- **解释范围扩大**：扩展到所有需要记忆的 agent 系统（对话记忆、长期知识、增量向量索引）
- **反例**：单层记忆（全部放向量库）→ 丢失时序精确性；全部全量快照 → 存储爆炸
- 层级：L4 Cognitive Model；证据强度 S5

## KO-06 失败可恢复性不变量（R3 不变量簇）
- **声明**：任何节点失败都不破坏线程状态一致性：异常被分层捕获→按策略重试/超时→错误处理器兜底→失败点状态已持久化（checkpoint）→可恢复可重放。失败是状态机的另一个合法转换。
- **簇内 EK**：EK-26（重试）/ EK-27（超时）/ EK-28（异常分层）/ EK-29（错误处理器）/ EK-30（错误写传播）/ EK-48（time-travel 回放）
- **边类型**：constraint（26/27/28 汇聚到"状态一致性不因失败破坏"）
- **解释范围扩大**：扩展到分布式工作流/长时运行任务的容错设计
- **反例**：进程崩溃丢内存态（无 checkpoint）；重试不持久化中间写 → 重复副作用
- 层级：L4 Cognitive Model；证据强度 S4（test_retry.py 2,944 行）

## KO-07 可插拔存储接口模式（R1 机制簇）
- **声明**：核心引擎只依赖三个抽象接口（CheckpointSaver/BaseStore/Serializer），实现全部外置（memory/postgres/sqlite + JsonPlus/Encrypted）；一致性靠契约测试套件（conformance）锁定而非靠共享实现。存储是插件不是引擎的一部分。
- **簇内 EK**：EK-12（saver）/ EK-36（serde）/ EK-37（白名单）/ EK-38（加密）/ EK-39（store）/ EK-40（conformance）
- **边类型**：mechanism（12↔39 同为存储接口；36↔37 同为 serde 机制）
- **解释范围扩大**：扩展到任何需要多后端持久化的框架（数据库 ORM、消息队列、缓存层）
- **反例**：存储耦合进引擎（实现分支散落业务代码）；无契约测试（实现漂移）
- 层级：L3 Pattern；证据强度 S4

## KO-08 增量计算复用（R1 机制簇）
- **声明**：增量语义（delta）被系统性地用于控制 checkpoint 体积：只存变化+种子，快照频率由（更新数,超步数）计数器自适应；同类思想在时间旅行、子图历史、迁移路径复用。增量计算是"成本-正确性"权衡的结构化解法。
- **簇内 EK**：EK-07（DeltaChannel）/ EK-47（delta 测试族）/ EK-40（conformance 覆盖）
- **边类型**：mechanism（07↔47 同一增量机制）+ dependency（47→40）
- **解释范围扩大**：扩展到增量备份、事件溯源、向量增量索引等"只存 diff"系统
- **反例**：全量快照每次（简单但体积线性增长）；增量无边界（历史链无限长）
- 层级：L3 Pattern；证据强度 S5（修复史最密集区）
