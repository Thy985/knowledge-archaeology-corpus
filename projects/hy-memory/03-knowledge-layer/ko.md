## KO-01 · 场景路由：成本与风险不对称时，先短路最低成本路径，失败一律退回最保守链路

- **aggregation_rule**: **R1 机制簇** — EK-01, EK-02, EK-03, EK-04, EK-05
- **layer**: **L3 Pattern**
- **epistemic**: Validated Pattern (single-project) · **strength**: S3 · **value**: A

### L1 · 事实
- `scene` 是封闭三值，非法输入在入口失败（EK-01）。
- 无 tool → O(1) 短路 chat，零 LLM（EK-02）。
- 含 tool 才调一次三分类（EK-03）。
- 分类三条失败路径全部 `defaulting to chat`（EK-04）。
- 强制 coding 但无 tool → 回退 chat（EK-05）。

### L2 · 为什么
写入是高频路径，分类是"为少数 coding 会话付出的固定成本"。因此先用**零成本可判定的条件**（有无 tool）过滤掉绝大多数请求；只有可能 coding 的请求才付费判定。判定失败时不报错而回退 chat：chat 是唯一不会误用生产力 schema 的通道，且原文仍被 L1 保存，信息不丢。

### L3 · 可复用模式
> **两级门控 + 保守降级**：先做 O(1) 的结构性前置判断（是否含 tool / 是否显式声明），只对可能命中的少数请求调用昂贵分类器；分类器任何失败都退回"信息不丢但功能最弱"的链路。

同类对照：
- Web 框架的"静态路由先匹配，未命中再进中间件链"。
- 编译器的"语法快速预判 → 必要时才 full parse"。
- 支付风控的"规则引擎先行，模型仅对灰名单打分"。

### 解释范围扩大论证
单看一条 EK 只是"某个 SDK 的 if 分支"。五条 EK 合起来给出一个**成本结构**：过滤条件必须是 O(1) 且高召回（无 tool 的对话确实不需要 coding memory）；失败方向的唯一正确选择由"哪种链路不丢数据"决定，而不是由"哪种链路更接近用户意图"决定。该结构可迁移到任何"多形态输入 + 昂贵分类器 + 不可丢数据"的入口。

### 反例预算（3 条，均未推翻，但限定适用范围）
1. **反例：分类器本身很便宜时，两级门控是多余复杂度。** 若分类是一次 embedding 相似度（<1 ms），直接分类比维护两级分支更简单。限定：**分类成本显著高于前置判断**时模式成立。
2. **反例：错误路由的代价高于漏路由时，fail-soft 会放大错误。** 若把 coding 记忆写进 chat 会导致后续检索永远找不到关键经验，而用户又不会检查，则"静默回退"是有害的。Hy-Memory 用 warning + `resp["variant"]` 暴露，但未提供对账机制——这是模式的一个真实缺口（见 C-01）。
3. **反例：显式声明应覆盖自动判定，但 Hy-Memory 仍要求 tool 前置。** 用户显式 `scene="coding"` 时系统仍然拒绝（EK-05）。这说明"显式意图"并没有最高优先级，**保守链路优先于用户意图**。可辩护（无 trace 无法抽取），但意味着 API 契约是"强制 = 在有 trace 时强制"。

**结论**：模式成立，但必须附带两个条件（分类成本高、下游有对账/可观测）。

## KO-02 · 写入的两级失败策略：不可重建的原文尽力写，可重算的派生要么全成要么全不成

- **aggregation_rule**: **R2 因果链簇** — EK-07 → EK-08 → EK-28
- **layer**: **L3 Pattern**
- **epistemic**: Validated Pattern (single-project) · **strength**: S3 · **value**: A

### L1 · 事实
- L1 raw 先 upsert；失败只记 `_l1_error`，继续（EK-07）。
- reconcile 失败 → 整批 0 条落库，无 ADD-all 兜底（EK-08）。
- 重跑依赖 `request_id` 幂等（EK-28）。

### L2 · 为什么
两类数据的**可重建性**不同：
- 原始对话不可重建（用户不会再说一遍），所以必须尽力落盘；
- 派生事实可从原文重算，但一旦写入错误的半成品（ADD-all 的重复/矛盾），版本链就被污染，且无法自动分辨哪条是脏数据。

因此同一写入路径里并存两种失败策略，不是不一致，而是按"数据可重建性"分层。

### L3 · 可复用模式
> **按可重建性分配失败语义**：源头数据（不可重建）用 best-effort + 告警；派生数据（可重算）用 all-or-nothing + 幂等重放。

同类对照：
- 数据库 WAL：日志先落盘（best-effort 保证不丢），页刷新失败可重放。
- 事件溯源：事件 append 成功才算发生；投影可重建。
- CI 产物：源码提交必须成功；构建产物失败可重跑。

### 解释范围扩大论证
三条 EK 原本分散在 writer 的不同分支。合起来给出一个可判定的分配规则：**问"丢了能不能重来"**。这比"重要数据要强一致、不重要数据可以弱一致"更可操作，因为重要性是主观的，可重建性是客观的。

### 反例预算（3 条）
1. **反例：原文也可能被重复写入。** best-effort 重试若没有幂等键，会在 L1 产生重复 raw；Hy-Memory 用 `request_id` 缓解（EK-28），但 L1 upsert 的幂等键是否覆盖所有入口，本轮未逐一验证（列为 C-03）。
2. **反例：all-or-nothing 在长批次上会放大尾延迟。** 一批 50 条候选，第 50 条失败则前 49 条全部丢弃并重跑，成本 ×2。若失败是持续性的（模型不可用），系统会永久卡住。Hy-Memory 没有"部分成功 + 标记待重算"的中间态。
3. **反例：可重建性会随时间变化。** 原文被裁剪（`raw_trim`）后，派生事实可能**不再可重建**；此时 all-or-nothing 的前提被削弱。裁剪规则与派生需求的耦合未被显式建模。

**结论**：模式成立，但要求"源头写入本身幂等"与"派生所需信息不被源头裁剪破坏"。

## KO-03 · 召回只暴露"当前有效语义"：状态机、链头、层白名单三处共同保证

- **aggregation_rule**: **R3 不变量簇** — EK-09, EK-10, EK-12
- **layer**: **L3 Pattern**
- **epistemic**: Validated Pattern (single-project) · **strength**: S3 · **value**: A

### L1 · 事实
- 删除 = SHADOW + `is_latest=False`，不物理删（EK-09）。
- 判重只取链头，链用于解释演化（EK-10）。
- 召回层是白名单 L2/L3/L4；L1 永不召回（EK-12）。

### L2 · 为什么
如果召回能看到历史版本或原文，模型会同时看到"旧结论"和"新结论"，并把冲突当成两个事实。系统选择让**检索面只呈现当前语义**，把"为什么变"留在链上按需展开。这是"读模型"与"写模型"的职责分离：写负责保留全部历史，读负责只给一个答案。

### L3 · 可复用模式
> **写侧全历史、读侧单语义**：存储保留所有版本与原文，但召回接口只返回当前有效集合；历史通过显式回溯通道访问。

同类对照：
- Git：对象库保留全部提交，`HEAD` 只给当前树。
- 事件溯源 + 物化视图：事件全存，查询走投影。
- 配置中心：版本全存，客户端只拿当前生效版本。

### 解释范围扩大论证
三条 EK 分属状态机、链管理、召回层三个模块，但共同维护一个不变量：**"搜索结果中的每个事实都是当前有效且已消解的"**。这个不变量可以独立于实现被检验（给任意 query，结果里不应同时出现 superseded 与其后继）。

### 反例预算（3 条）
1. **反例：审计/合规场景需要"当时的口径"。** 只给当前语义会让"某年某月的结论"不可复现。Hy-Memory 的链可回溯，但没有"as-of 查询"（按时间点召回）。限定：模式适用于**在线问答**，不适用于审计查询。
2. **反例：SHADOW 复用给"低置信度推断"，与"已删除"混在同一状态。** 两者在召回上都不可见，但语义不同：一个是"不确定"，一个是"不成立"。合并状态会让运维无法区分"缺证据"与"被推翻"。这是实现层的一个语义压缩（见 C-04）。
3. **反例：L1 不召回使"原文定位"必须二次查询。** 当用户问"原话是什么"，系统无法直接从召回结果回答，需要额外的 raw 通道。Hy-Memory 通过 `source_raw_memory_id` 提供指针，但是否有公开 API 本轮未验证。

**结论**：不变量成立；边界是"在线读取"而非"历史审计"。

## KO-04 · 事实保底、经验增值：任务轨迹无阈值，复用知识要过价值判断

- **aggregation_rule**: **R4 主题簇** — EK-15, EK-16
- **layer**: **L2 Engineering Knowledge**（不升 L3：证据面仅覆盖 coding 子系统，簇规模 2）
- **epistemic**: Engineering Experience · **strength**: S3 · **value**: A

### L1 · 事实
- 每 session 恰 1 条 WorkingFact；Experience 0~N（EK-15）。
- value bar 在抽取判断中，非硬编码（EK-16）。
- 双向 id 链取并集回写（EK-15）。

### L2 · 为什么
"这次做了什么"是**可验证的历史**，丢失即不可恢复；"从这次学到什么"是**归纳**，质量不稳定，强行产出会污染经验库。因此对两类记忆采用不同的准入策略：事实无条件记录，经验按价值门槛筛选。

**为什么停在 L2**：这是一种具体的工程取舍，尚未在第二个项目/第二种任务类型上验证；把它升为"所有 Agent 记忆都应双层"会超出证据。

## KO-05 · 代码版本链：用确定性 diff 补摘要丢失的信息，但只做检索的附件

- **aggregation_rule**: **R2 因果链簇** — EK-17 → EK-19 → EK-20/EK-21 → EK-22
- **layer**: **L3 Pattern**
- **epistemic**: Validated Pattern (single-project) · **strength**: S3 · **value**: A

### L1 · 事实
- 链零 LLM、零 embedding（EK-17）。
- patch 三来源，合成 diff 行号不可信 → 按 symbol 归并（EK-19）。
- 失败编辑不入链（EK-20）；git 不可用静默退化（EK-21）。
- 链只装饰检索结果，写入失败跳过（EK-22）。

### L2 · 为什么
抽取规范为了省 token 会主动丢弃代码（"给坐标不要贴代码"），这是有损压缩。为了在"未来需要精确改法"时能还原，必须有一条**不经过模型**的旁路记录真实 diff。但它不能成为第二检索源：两条通道会各自排序、互相矛盾，且链没有语义索引，无法回答"哪段代码和这个问题相关"。

### L3 · 可复用模式
> **无损旁路 + 单检索权威**：对"摘要必然丢失、但未来可能需要"的信息，建一条确定性的、只追加的旁路存储；召回仍由语义层决定，旁路只按主结果的键挂载。

同类对照：
- 数据库的 binlog：不参与查询，但可按主键回放。
- 影像系统的 DICOM 原始层 + 语义索引层。
- 代码搜索的"符号索引（主）+ 原文片段（附件）"。

### 解释范围扩大论证
五条 EK 构成完整链：为什么不用模型（保真）→ 怎么拿 patch（三来源）→ 怎么防脏（拒收）→ 怎么消费（附件）。这回答了一个通用问题：**"有损摘要系统如何保留可还原性，同时不制造第二真相源"**。

### 反例预算（3 条）
1. **反例：旁路会无限增长且无 GC。** `thread.body` 每轮覆写、`round` 只追加；没有保留策略。长期使用会成为存储与隐私负担（代码里可能含密钥）。Hy-Memory 未展示清理机制（C-05）。
2. **反例：零 LLM 意味着无法处理非 diff 形式的变更。** sed / heredoc / IDE 批量重构不会被合成（EK-19 明确"不猜"）。在高比例非 diff 工作流中，链会大量缺轮。
3. **反例："只做附件"使链无法被独立检索。** 当用户问"这个函数历史上改过几次"而向量层没有对应 fact 时，链查不到。这是设计取舍，不是缺陷，但限定了使用场景。

**结论**：模式成立；必须补保留策略（否则从"附件"变成"负债"）。

## KO-06 · 管理面不得复制引擎权威：产品层只存外键，授权绑定身份

- **aggregation_rule**: **R3 不变量簇** — EK-23, EK-24, EK-27
- **layer**: **L3 Pattern**
- **epistemic**: Validated Pattern (single-project) · **strength**: S3 · **value**: A

### L1 · 事实
- MemHub 不存正文、不判 supersede、只存 memory_id（EK-23）。
- 来源授权校验 `root_identity`，变化即拒（EK-24）。
- 本地 API 用 IP 解析防 DNS rebinding（EK-27）。

### L2 · 为什么
一旦产品层能写正文或判 supersede，就会出现两份"当前真相"，且同步失败时无法判定谁对。把产品层压成"管理面"是用**能力缺失**换一致性。同理，授权若只校验路径字符串，旧授权会被新内容继承；绑定身份使"换了内容"必然触发重新确认。

### L3 · 可复用模式
> **单一写入权威 + 外键化产品层 + 身份化授权**：产品层只能引用引擎 ID；任何派生状态由引擎判定；对外部资源的访问权绑定资源身份而非名称。

同类对照：
- 对象存储的"元数据服务只存 object id，不存副本"。
- OAuth 的 token 绑定 client 身份而非回调 URL 字符串。
- K8s 的 admission webhook：策略在控制面，工作负载不自行改写。

### 解释范围扩大论证
三条 EK 表面分属架构、授权、安全，但共享同一不变量：**"谁有权定义当前状态"必须唯一**。产品层、路径字符串、Origin 前缀，都是"看似方便的第二权威"，模式要求把它们降级为引用/校验。

### 反例预算（3 条）
1. **反例：产品层完全无缓存会让高频 UI 每次穿透 SDK。** MemHub 仍需列表/队列等读模型；"只存外键"不等于"零派生数据"。若派生视图与引擎不一致，仍会出现"UI 显示的记忆已被 supersede"。代码中未见缓存失效协议（C-06）。
2. **反例：身份校验对"内容原地修改"无效。** 若目录身份不变但内部文件被替换（同名覆盖），`root_identity` 仍匹配。它防的是"路径指向变了"，不是"内容变了"。
3. **反例：Origin 白名单在非浏览器客户端（CLI/桌面）无意义。** 桌面端用 `one-memory://app` 自定义 scheme，其他本地进程可直接带 Bearer 调用；安全边界实际是"本机 + token"，不是"浏览器同源"。

**结论**：不变量成立；需补充派生视图的失效协议与内容级完整性校验。

## KO-07 · 隔离不靠调用方声明，靠"键里包含所有会碰撞的维度"

- **aggregation_rule**: **R1 机制簇** — EK-11, EK-18, EK-25, EK-26
- **layer**: **L4 Cognitive Model**（`Cross-project validation pending`）
- **epistemic**: Hypothesis→Pattern，未跨项目验证 · **strength**: S3 · **value**: A

### L1 · 事实
- chat 判重按 owner 分组（user 跨 agent / agent 隔离）（EK-11）。
- chain 的 `owner = user|workspace` 必须进键，否则串链（EK-18）。
- user_id 禁 `:`，lane key 用 `@`（EK-25）。
- workspace scope 只能由 cwd 解析，不能凭空声明（EK-26）。

### L2 · 为什么
四个子系统选择了同一种做法：**不把"当前用户是谁"作为运行时参数传递，而把它写进每一个存储键**。因为参数会被漏传、会被默认值覆盖、会在某条分支被遗忘；键不会——键错了就查不到，故障是显性的。字符集约束（禁 `:`）则消除了键拼接的歧义。

### L3 → L4 · 稳定关系（一句话）
> **在多租户系统中，隔离的可靠性等于"所有会碰撞的业务键都已被隔离维度前缀化"的程度，而不等于权限检查的覆盖率。**

这是从"检查"到"身份编码"的视角转换：权限检查是**事后拦截**（漏一处即泄漏），键前缀化是**结构性不可达**（没有正确的键就构造不出查询）。

### 解释范围扩大论证（L3→L4 的必要条件）
- 四个独立子系统（判重分组 / 代码链 / 用户 lane / 工作区解析）重复出现同一做法 → 不是单点实现。
- 每个案例都有"不加维度 → 具体故障"的显式证据（串链、读他人 history、默认召回为空）。
- 反例可检验：若某处只做权限检查而未前缀化，应能找到绕过路径。

### 反例预算（3 条）
1. **反例：前缀化不能替代授权。** 知道键构造规则的人仍可伪造键（若 API 接受任意 scope）。Hy-Memory 用"只能解析自己 cwd"堵住 workspace，但 user_id 仍由调用方传入——**用户维度是声明式的，不是从认证态推导的**。这是该模型的边界：键前缀化防"误撞"，不防"故意构造"。
2. **反例：键维度增加会破坏兼容性。** chain 加 owner 需要老库迁移（补列 + 重建索引）；若迁移遗漏，历史链会归到错误 owner。结构性隔离的代价是**迁移必须一次做对**。
3. **反例：维度爆炸。** 每增加一个隔离维度（tenant/team/project/workspace/branch），键组合与索引基数上升；过度前缀化会让查询必须带全维度，降低灵活性。模型要求"只包含**会碰撞**的维度"，但"会碰撞"本身需要领域判断。

**结论**：作为 L4 认知模型成立，但必须同时声明两个边界：**声明式维度不等于认证**；**前缀化有迁移与基数成本**。跨项目验证待办（Mem0/Graphiti/Letta 是否有同类做法，本轮未做对照实验）。
