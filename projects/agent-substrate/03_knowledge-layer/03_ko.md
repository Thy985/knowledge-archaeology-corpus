## KO-01 幂等恢复以"持久化状态为真相源"：重入从状态推导进度而非重跑工作流
- **层**：L4 Cognitive Model
- **aggregation_rule**：R2 因果链簇（EK-01 → EK-02 → EK-06 → EK-07 沿 causal 边形成"重入→状态推进→幂等恢复"完整链）
- **簇内 EK**：EK-01（ResumeActor 幂等）、EK-02（worker 认领可重入）、EK-06（CheckpointContext 去取消）、EK-07（checkpoint-done + BootID 复用）、EK-09（UID 钉化身）
- **模型陈述**：在分布式生命周期系统中，**幂等 = 每一步完成后持久化中间状态，重入时以持久状态为真相源 fast-forward 已完成步骤**，而非重放工作流；版本冲突（Aborted）返回让调用方重试而非覆盖。
- **解释范围扩大**：从"actor resume"推广到任何有状态分布式工作流（K8s controller reconcile、Dapr actor 恢复、数据库迁移器）。
- **证据强度**：S3-S4（代码实现 + 重入路径注释 + 版本前提冲突返回 Aborted）。
- **反例**：见 06 Validation——若中间状态持久化缺失（如 volume 创建部分失败仍持久化）则 fast-forward 不可靠；Substrate 特意"部分失败也持久化更新状态"来保幂等（EK-01 证据）。
- **跨项目**：Dapr Agents（10-30 考古）崩溃恢复按事件日志重放——对照见 KO-07。

## KO-02 短暂瞬态（blip）可重试，决定/缺陷不重试：重试预算按信号衰减定价
- **层**：L4 Cognitive Model
- **aggregation_rule**：R1 机制簇（EK-08/EK-16/EK-05 共享"错误分类→重试决策"机制边，跨 ≥2 独立子系统：worker suspend 上行、egress 网关、router parking）
- **簇内 EK**：EK-08（suspend 只认 Unavailable/Aborted/ResourceExhausted）、EK-16（凭据注入 403 vs 503 映射）、EK-05（parking 把 ResourceExhausted/Unavailable 当 retryable）
- **模型陈述**：**重试策略的第一性问题不是"重试几次"，而是"哪些错误值得重试"**：瞬态（服务不可达/背压/租约争用）重试，决定（NotFound/FailedPrecondition/被拒）不重试，缺陷（PermissionDenied/InvalidArgument）重试无益，超时类（DeadlineExceeded）重试会翻倍等待必须按语义单独定价。
- **解释范围扩大**：gRPC/HTTP 客户端、任务调度器、网关代理的通用重试设计。
- **证据强度**：S3（三处独立实现同一分类法 + 详细注释）。
- **反例**：DeadlineExceeded 在 parking 语境被当 retryable（EK-05 把超时后的错误按容量 503 表面）——与 suspend 的"DeadlineExceeded 不重试"相反，说明分类依语义而非错误码字面（见 06 Validation Counterexample-2）。
- **跨项目**：Cross-project validation pending（对照 dapr-agents 的 retry policy）。

## KO-03 请求停车（parking）与提交承诺分离：预算限新尝试，不取消已承诺工作
- **层**：L3 Pattern（高价值工程模式）
- **aggregation_rule**：R4 主题簇（EK-05/EK-02/EK-10 围绕"超卖下 ingress 请求处理"主题互补维度）
- **簇内 EK**：EK-05（parking 预算语义）、EK-02（ResourceExhausted 来源）、EK-10（ingress mTLS CONNECT 路径）
- **模式陈述**：超卖系统中，对"暂不可服务但即将可服务"的请求采用**有界停车**：指数退避重试直到成功或预算到期；**预算只停止发起新尝试，绝不取消已提交给控制面的 in-flight 操作**（取消会丢弃已承诺的 restore）；超预算恢复"晚到服务"而非失败。
- **同类对照**：HTTP 503 + Retry-After；gRPC 客户端退避；K8s reconcile requeue。**差异**：parking 在代理层持有请求体并主动重试 resume，且不 cancel 已提交操作。
- **证据强度**：S3 + 文档（request-parking.md 明确 budget semantics）。
- **反例**：若 resume 永远无法完成（如 actor 永久损坏），parking 只是延迟失败——预算到期仍 503；#3472 把 FailedPrecondition 改快速失败说明"决定类错误不该 parking"。
- **跨项目**：Cross-project validation pending（与 Dapr 的 retry 对照见 KO-07）。

## KO-04 沙箱内零凭据 + 网关外注：凭据永不出现在工作负载运行时
- **层**：L4 Cognitive Model（安全模型）
- **aggregation_rule**：R3 不变量簇（EK-18/EK-17/EK-19 经 constraint/dependency 边汇聚到同一安全不变量"actor 无凭据"）
- **簇内 EK**：EK-18（零凭据沙箱）、EK-17（身份来自 mTLS 证书非请求头）、EK-19（SPIFFE X.509 + on-demand JWT）、EK-24（组件全 mTLS）
- **模型陈述**：**工作负载身份与凭据分离**：身份（identity）由基础设施签发（SPIFFE/短期证书），凭据（credential）在沙箱外按策略注入；沙箱内无凭据可窃取、无凭据可滥用。身份永远来自加密握手而非可伪造的请求头。
- **解释范围扩大**：Sidecar 模式、SPIFFE 生态、云厂商 secret 注入的通用安全原则。
- **证据强度**：S3（security.md Met + egress credentials.go 实现）。
- **反例**：见 06 Validation——OIDC/credential provider 是控制面外系统（credprovider.proto 存在）；credential 若 provider 未配置则 403 fail-closed（EK-16），不降级为弱认证。
- **跨项目**：Cross-project validation pending（与 Strands Box / MXC 跨厂商"credentials outside the box"共识对照——见 Candidates C-1）。

## KO-05 双重授权原则：涉及用户数据/持久状态的操作需多方身份共同见证
- **层**：L4 Cognitive Model
- **aggregation_rule**：R3 不变量簇（EK-21/EK-22/EK-23 经 mechanism/constraint 边汇聚到"无单点授权"不变量）
- **簇内 EK**：EK-21（双重快照授权 actor+atelet）、EK-22（AssetPlugin sha256 pin）、EK-23（OpenFGA bootstrapOwners contextual tuple）
- **模型陈述**：**高价值操作（快照读写、凭据释放、全局授权）不应由单一主体全权决定**：快照读写需 actor+节点 supervisor 双身份；资产需 size+sha256 双校验；全局 owner 用 contextual tuple 防 API 撤销。
- **解释范围扩大**：云 KMS 双重控制、密码学 split-key、四眼原则的工程实现。
- **证据强度**：S3（security.md Met + objectstoreplugin/exchange + authz/authorizer.go）。
- **反例**：S3 per-actor tokens 是 Future（EK-21）——双重授权未全平台覆盖；Atespace 网络策略/配额也 pending（security.md）。
- **跨项目**：Cross-project validation pending。

## KO-06 文档目标态 ≠ 实现态：自标状态图例是安全的文档纪律
- **层**：L5 Methodology
- **aggregation_rule**：R4 主题簇（EK-34/EK-35/EK-40 与文档纪律相关维度 + Project Layer 1.8 事实）
- **簇内 EK**：EK-34（Delete Guarantee 标 In Progress）、EK-35（Dynamic Quarantine 分 Met/Future）、EK-40（v1.0 前无强制的互不透明）+ docs 标注事实
- **方法陈述**：**大规模系统文档必须显式区分"目标态/已实现/进行中/未来/范围外"**，且北极星指标要标注为目标而非已验证事实；考古与工程协作时，实现事实只能从代码/测试取，文档仅提供设计意图。
- **可操作准则**：①文档 front matter 标 status；②每个安全/架构原则带状态图例；③README 性能数字标注 target vs measured；④以 e2e 测试为实现态锚点。
- **证据强度**：S3（本仓库 practice）+ 跨项目经验待验证。
- **反例**：若文档状态标注过期（代码已实现但文档仍标 Future），读者会低估能力——本考古无法验证标注新鲜度，留 Candidates C-4。
- **跨项目**：Cross-project validation pending。

## KO-07 生命周期管理两条路线对照：suspend-resume（状态快照）vs 崩溃恢复（事件重放）
- **层**：L3 Pattern（跨项目对照）
- **aggregation_rule**：R4 主题簇（EK-04/EK-06/EK-07/EK-08 围绕"actor 生命周期暂停/恢复"主题）+ 与 dapr-agents 考古的跨项目对照
- **簇内 EK**：EK-04（上行/下行分离）、EK-06（CheckpointContext）、EK-07（checkpoint-done+BootID）、EK-08（suspend 重试预算）
- **模式陈述**：**让"暂停的工作负载"重新可服务有两条路线**：①F1 suspend-resume：把完整运行状态（内存+数据）快照，恢复时还原（Substrate——代价：快照大、恢复重、需双授权）；②F2 崩溃恢复：持久化执行轨迹/事件，崩溃后重放或重演（Dapr Agents——代价：非确定性步骤需幂等重试）。Substrate 用 BootID 界定快照有效性、用 checkpoint-done 标记幂等复用，是 F1 路线的高密度优化。
- **同类对照**：容器 CRIU、VM live migration（F1）；事件溯源/outbox pattern（F2）。
- **证据强度**：S3（Substrate 实现）+ S8 部分（与 dapr-agents 10-30 考古对照）。
- **反例**：F1 对"不可快照工作负载"（GPU 状态、外部会话）失效；F2 对"必须精确还原内存"失效。二者互补而非替代。
- **跨项目**：与 dapr-agents 形成实证对照（10-30 轮 corpus 已有），模式级别跨项目成立，原则级仍需更多项目验证。
