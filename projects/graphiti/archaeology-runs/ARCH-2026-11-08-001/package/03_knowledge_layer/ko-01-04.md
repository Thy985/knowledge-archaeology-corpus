# Knowledge Layer · KO-01 ~ KO-04

## KO-01 事实不是"值"，而是"带时间窗与来源的断言"
- **aggregation_rule**: **R1 机制簇**（`mechanism` 边：EK-02 ↔ EK-03 ↔ EK-10；跨 3 个独立子系统——节点模型 / 边模型 / 检索过滤）
- **cluster**: EK-02, EK-03, EK-04, EK-10, EK-11
- **L1 事实**: `EntityEdge` 同时携带 `valid_at/invalid_at/expired_at/reference_time` 与 `episodes[]`；episode 保存原始 `content`；变更时新增边并失效旧边，不覆盖文本（E-05, E-10, E-26）。
- **L2 工程知识**: 之所以不覆盖，是因为"事实"在真实世界会演变；覆盖会丢失"当时为真"的历史，也无法解释"为什么 Agent 现在这样回答"。流失历史 = 失去可审计性。
- **L3 Pattern**: 任何长期记忆系统若要支持"当时/现在"两种查询与事后审计，必须把**内容、时间、来源**三者绑定为同一记录单元，而不是只存最终值。
- **L4 Cognitive Model**: **记忆 = 带时间戳与溯源的断言集合；不是状态快照。** 状态快照只回答"现在是什么"，断言集合回答"曾经/现在/为什么"。
- **L5 Methodology**: 设计记忆 schema 时，先定义时间语义（业务时间 vs 系统时间）与 provenance 字段，再谈检索；删除一律走"失效/引用计数"，不做物理覆盖。
- **evidence**: E-05, E-10, E-13, E-26
- **epistemic**: `Pattern (Graphiti-originated, strongly evidenced, cross-project validation pending)`
- **解释范围扩大论证**: 从"Graphiti 的 Edge 有四个时间字段"（实现）→"记忆应是带时间窗的断言"（跨系统可用）。反例压力：若只做短期会话缓存，时间窗是过度设计——因此范围限定为"长期/需审计的记忆"。
- **反例**: Mem0 v3 走 ADD-only + 检索时融合，不维护 `invalid_at`，也能工作（corpus 已有，待对照）。→ 说明时间窗不是唯一解，是**需要历史查询时的必选**。

## KO-02 写入是"渐进管线"，每一步都在缩小不确定性
- **aggregation_rule**: **R2 因果链簇**（`causal` 链 EK-01 → EK-13 → EK-03 → EK-04 → EK-11；覆盖抽取→hydration→时间→失效→持久化）
- **cluster**: EK-01, EK-11, EK-12, EK-13, EK-04
- **L1 事实**: 七阶段顺序固定；边解析依赖节点 `uuid_map`；属性抽取只接收新边；时间戳在边解析后由 LLM 补（E-11~E-17, E-28）。
- **L2 工程知识**: 把"抽取"和"裁决"拆成独立阶段，才能在不牺牲精度的前提下控制 LLM 调用次数：抽取一次批量、裁决只处理未决集。
- **L3 Pattern**: 高不确定输入（自然语言）→ 结构化 → 与既有状态比对 → 冲突处理 → 持久化，是一条**渐进降不确定**的管线；每阶段都应可单独测试与观测。
- **L4 Cognitive Model**: **写入不是一次转换，而是一串可观测的判定。** 把判定拆开，错误才能定位到具体阶段（抽取错 / 去重错 / 时间错 / 失效错）。
- **L5 Methodology**: 为写管线建立阶段级 span 与计数（Graphiti 用 OTEL attributes：node.count / edge.count / edge.invalidated_count），让"哪一阶段异常"可观测。
- **evidence**: E-11~E-17, E-28
- **epistemic**: `Pattern (Graphiti-originated, strongly evidenced, cross-project validation pending)`
- **反例**: `add_episode_bulk` 合并部分阶段以减少往返（E-1588 存在），说明阶段可合并——但合并会牺牲"阶段级可观测性"，是吞吐 vs 可诊断的权衡。

## KO-03 去重的成本纪律：确定性规则优先，LLM 只做最后裁决
- **aggregation_rule**: **R1 机制簇**（`constraint` + `mechanism`：EK-07 ↔ EK-08 ↔ EK-09；跨 3 个独立实现点——候选采集 / 语义检索 / LLM 裁决）
- **cluster**: EK-07, EK-08, EK-09
- **L1 事实**: 候选三路合并；identity → cosine(0.6, top15) → LLM；LLM 只处理未决集合；能力缺失时返回空集并继续（E-20~E-24, E-41）。
- **L2 工程知识**: 每实体调用一次 LLM 去重会线性放大成本与延迟；先用确定性键（identity/精确名）与向量粗筛，把 LLM 的输入压到"真正模糊"的少数，是成本与精度的折中。
- **L3 Pattern**: **分层裁决（tiered adjudication）**：规则/索引 → 相似度 → 模型裁判，逐层缩小候选。任何"用模型替代全部匹配"的设计都会在规模上失效。
- **L4 Cognitive Model**: **确定性与概率性应分层，而不是二选一。** 确定性负责"可解释的多数"，概率性负责"模糊的少数"。
- **L5 Methodology**: 为每层设预算（候选上限、相似度阈值、批量大小），并把"未决率"作为可观测指标；未决率异常升高时先查上游抽取质量，而不是调大模型。
- **evidence**: E-20~E-24, E-41
- **epistemic**: `Pattern (Graphiti-originated, strongly evidenced, cross-project validation pending)`
- **反例**: 若实体名高度不规范（多语言/别名），identity 与精确名命中率低，几乎全部落到 LLM——分层退化为"全模型"。此时应补别名表/规范化，而非直接调阈值。

## KO-04 请求级状态隔离是并发正确性的前提，不是性能优化
- **aggregation_rule**: **R3 不变量簇**（`constraint` 汇聚到同一不变量："任何请求的执行路径不得依赖可被其他请求改写的实例状态"；EK-05, EK-33, EK-21 从写路径、读路径、LLM 路径三个面汇聚）
- **cluster**: EK-05, EK-33, EK-21
- **L1 事实**: `#1676` 并发改写 `self.driver` → 数据写入错误 graph；`#1659` 单 group 查询走默认库 → 静默空结果；`#1758` decorator 参数错位 → TypeError。修复统一为 per-call 绑定 + 显式传递（E-18, E-19；`decorators.py` 注释）。
- **L2 工程知识**: 这些 bug 的共同前提是"协程在大量 await 点之间共享可变实例状态"。只要状态在调用期间可被他人改写，正确性就无法由代码评审保证。
- **L3 Pattern**: **Per-request scope（请求级作用域）**：把请求相关的依赖（连接、租户、模型）作为参数沿调用链传递，或放入请求上下文；禁止在 `self` 上按请求改写。
- **L4 可迁移关系（降级后）**: **并发安全 = 消除隐式共享，而不是加锁。**（本项目内成立，跨项目待验证） 加锁能防交错，但会串行化吞吐；请求级作用域既保正确性又保留并发。
- **L5 Methodology**: 审查任何异步服务时，先找"`self.x = ...` 出现在 await 前后"的位置；把这些赋值改为返回值/参数传递，并用并发测试固定（Graphiti 已有 `test_concurrent_completes_do_not_serialize_or_clobber_model`，E-46）。
- **evidence**: E-18, E-19, E-46
- **epistemic**: `Pattern (Graphiti-originated, 3 regression sites but single project/team/stack; 独立审计由 Principle 降级; cross-project validation pending)`
- **audit_note**: 三条回归同仓库同维护者，不构成跨项目证据；"principle" 改为 "strong pattern"。
- **反例**: 单租户、单连接的 CLI 用法不存在共享冲突——此时 per-request scope 是多余开销（Graphiti 对默认库路径刻意"不 clone 不 copy"正说明这一点，E-18）。
