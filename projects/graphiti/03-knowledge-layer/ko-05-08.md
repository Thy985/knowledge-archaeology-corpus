# Knowledge Layer · KO-05 ~ KO-08

## KO-05 分区键同时是"租户语义"与"物理存储语义"
- **aggregation_rule**: **R4 主题簇**（覆盖同一主题的互补维度：逻辑隔离 EK-06 / 后端选择 EK-18 / 后端并发缺陷 EK-31）
- **cluster**: EK-06, EK-18, EK-31, EK-05
- **L1 事实**: `group_id` 是逻辑分区；FalkorDB 下 `group_id` 同时决定 graph 名，必须 `clone(database=gid)`；Neo4j/Neptune 在同库过滤。FalkorDB 并发查询会断连（E-04, E-06, E-18, E-53）。
- **L2 工程知识**: 同一抽象（"分区"）在不同后端被映射为不同物理机制；一旦物理映射变化，"读不到"和"读错库"就会以静默方式发生。
- **L3 Pattern**: **逻辑分区键与物理存储映射必须显式建模**（映射函数、默认分支、越界行为），且每个后端要有独立的一致性测试。
- **L4 Cognitive Model**: **"隔离"不是布尔值，而是"逻辑键 × 物理实现 × 失败模式"的三元组。** 只声明逻辑隔离，无法保证物理隔离。
- **L5 Methodology**: 多租户设计时：① 明确分区键；② 为每个后端写"跨分区不可见"与"单分区可路由"两类测试；③ 把默认库路径当作特例显式处理（Graphiti 的"默认库不 clone"即此）。
- **evidence**: E-04, E-06, E-18, E-53
- **epistemic**: `Pattern (Graphiti-originated, strongly evidenced, cross-project validation pending)`
- **反例**: 单后端部署（只用 Neo4j）不会遇到 FalkorDB 的映射问题——此时三元组退化为"逻辑键 + 单实现"。

## KO-06 开源框架的"能力"必须以托管边界为界，不得混记
- **aggregation_rule**: **R3 不变量簇**（约束："凡是仓库中不存在实现的能力，不得记为仓库能力"；EK-26, EK-27, EK-22 从产品定位、安全声明、服务定位三处汇聚）
- **cluster**: EK-26, EK-27, EK-22
- **L1 事实**: README 明确 Graphiti 是 BYO 框架、Zep 提供治理/Konig/用户线程/SLA；SECURITY 明确参考服务无认证授权；server/mcp 是 reference implementation（E-51, E-52）。
- **L2 工程知识**: 厂商把"开源内核"与"托管治理"分产品线，是常见商业模式；考古时若把 README 的营销语句当作能力事实，会高估开源仓库。
- **L3 Pattern**: **能力分层记账（capability layering）**：framework / reference implementation / managed platform 三层，分别标注证据来源，禁止跨层外推。
- **L4 可迁移关系（降级后）**: **"有没有这个能力"取决于"在哪个交付物里"**。同一品牌下，能力可能只存在于闭源侧。
- **L5 Methodology**: 考古/尽调时，对每条能力问三句：代码里有没有？测试里有没有？文档说的是本仓库还是托管产品？三者不一致时以代码为准。
- **evidence**: E-51, E-52
- **epistemic**: `Pattern (Graphiti-originated; 独立审计由 Principle 降级：仅 2 份文档，无跨项目对照)`
- **反例**: 某些项目 README 与代码一致（如 go-sdk），此时三层记账退化为"一层"，但仍应保留来源标注。

## KO-07 记忆的信任边界只到分区，投毒在该信任模型下成立
- **aggregation_rule**: **R4 主题簇**（互补维度：信任声明 EK-28 / 工具暴露面 EK-29 / 删除语义 EK-24 / 分区 EK-06）
- **cluster**: EK-28, EK-29, EK-24, EK-06
- **L1 事实**: 官方声明"同 group 内所有 episode 同等信任，新 episode 可改变/失效旧事实"；MCP `clear_graph` 无权限检查；删除按引用计数而非来源可信度（E-49, E-51）。
- **L2 工程知识**: 图的写入只校验"格式/类型/时间"，不校验"来源是否可信"；因此任何能调用写接口的内容提供方，都能改写记忆。
- **L3 Pattern**: **信任边界必须与写入边界对齐**。若信任只到分区，则分区内的所有写入者必须被视为同等权限主体；否则需要"来源级"策略（签名、白名单、评分）。
- **L4 可迁移关系（降级后）**: **在该信任模型下，记忆系统的安全强度 ≈ 写入准入强度；检索过滤不能撤销已写入的污染。** 检索端过滤只能减少暴露，不能撤销已被写入的污染。
- **L5 Methodology**: 设计记忆系统时，把"谁能写、写到哪个分区、写入是否需要审批/签名"作为第一类问题；对不可信来源使用独立分区 + 只读合并，而不是共享分区。
- **evidence**: E-49, E-51, E-06
- **epistemic**: `Pattern (Graphiti-originated; 独立审计由 Principle 降级：单一 SECURITY 文档 + 未实测投毒)`
- **反例**: 单用户个人助理场景，所有内容来自同一用户，信任边界=分区是合理简化。

## KO-08 多后端"可插拔"不等于"行为等价"，能力缺失必须可观测
- **aggregation_rule**: **R1 机制簇**（`mechanism` + `contrast`：EK-17 ↔ EK-19 ↔ EK-32 ↔ EK-31；跨 4 个实现点——ABC/命名空间/弃用面/后端并发）
- **cluster**: EK-17, EK-19, EK-32, EK-31
- **L1 事实**: 驱动 ABC + `NotImplementedError` 降级；Kuzu 弃用；FalkorDB 并发断连；`_search` 弃用；spec 的 Namespace 重构仍在 Phase 1（E-33, E-38~E-43, E-53）。
- **L2 工程知识**: 用异常表达"能力缺失"能让新后端渐进接入，但会把"不支持"与"没结果"折叠成同一个返回值（空列表），使调用方无法区分。
- **L3 Pattern**: **能力矩阵 + 显式 unsupported 信号**：每个后端声明支持的操作集合，调用不支持的操作返回可区分的错误/能力标记，而不是空结果。
- **L4 Cognitive Model**: **抽象层的价值取决于它对差异的显式程度。** 抽象若掩盖差异，使用者会在生产环境才发现行为不一致。
- **L5 Methodology**: 多后端系统必须维护"能力矩阵测试"（同一用例跑所有后端并比对语义），并把弃用/降级路径写入文档与指标。
- **evidence**: E-33, E-38~E-43, E-53
- **epistemic**: `Pattern (Graphiti-originated, strongly evidenced, cross-project validation pending)`
- **反例**: 只支持单后端的库不需要能力矩阵；此时"可插拔"只是接口预留，不构成承诺。
