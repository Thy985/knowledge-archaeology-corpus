# 02.2 Engineering Knowledge · EK-16 ~ EK-30

---

## EK-16 空 `InputRequests` 被复用为负载卸载信号

- **Level**: L2
- **Statement**: `CallToolResult.NeedsInput()` 为 true（`resultType=input_required`）且 `InputRequests` 为空时，官方注释明确这是 **load-shedding**。
- **Why**: 复用同一结果类型可以避免新增 `resultType` 或 HTTP 状态码；客户端只需要"再试一次"，至于是"缺输入"还是"服务器过载"，由 `InputRequests` 是否为空区分。
- **Evidence**: E-34
- **Links**: `mechanism` ↔ EK-15；`contrast` ↔ EK-18
- **Value**: B
- **Epistemic**: Fact

## EK-17 新协议用每请求 `_meta` 自描述，不依赖握手残留状态

- **Level**: L2
- **Statement**: `injectRequestMeta` 为每个出站请求注入 `protocolVersion`，并按配置附带 `clientInfo`/`clientCapabilities`；已存在的 key 不被覆盖。
- **Why**: 无状态服务端不能假设"上一次请求的握手结果还在"；每个请求自带版本与能力，才能被任意实例独立处理。
- **Evidence**: E-46
- **Links**: `mechanism` ↔ EK-18；`dependency` → EK-05
- **Value**: A
- **Epistemic**: Observation

## EK-18 版本校验分三平面：HTTP header（旧）/ `_meta`（新）/ 握手（旧）

- **Level**: L2
- **Statement**: `validateProtocolVersion` 只对 `<2026-07-28` 的 `MCP-Protocol-Version` header 报 400；≥2026-07-28 的未知版本不在 HTTP 层拒绝，交由 `discover` 与每请求 `_meta` 处理。
- **Why**: 新协议允许客户端在 body 中声明版本（甚至同一连接多版本），HTTP header 只是"旧协议的路由提示"，不能成为新协议的硬门禁。
- **Evidence**: E-45, E-46
- **Links**: `mechanism` ↔ EK-17；`contrast` ↔ EK-16；`constraint` → EK-03
- **Value**: A
- **Epistemic**: Observation

## EK-19 断点重放被设计成外部 EventStore 契约

- **Level**: L2
- **Statement**: `EventStore` 需实现 `Open/Append/After/SessionClosed`；`After` 必须"一旦数据被丢弃就立即报错，不得返回部分结果"；无 EventStore 时不能 replay。
- **Why**: SDK 不想内置持久化（部署方可能用 Redis/DB/对象存储）；把契约写死在接口上，保证不同实现有一致语义——尤其是"部分重放"比重放失败更危险。
- **Evidence**: E-35, E-37
- **Links**: `subsystem` ↔ EK-20；`dependency` → EK-21；`mechanism` ↔ EK-05（无状态下的可恢复性）
- **Value**: A
- **Epistemic**: Observation

## EK-20 同一 stream 的并发 replay 被独占锁拒绝（409）

- **Level**: L2
- **Statement**: `acquireStream` 对已结束的 stream 建临时条目并独占 replay；若 `s.w != nil` 且非临时，返回 409 `stream ID conflicts with ongoing stream`。
- **Why**: 两个客户端同时用同一个 `Last-Event-ID` 重连会造成事件被拆分到两个响应；独占可以保证"一个 stream 只有一个 writer"。
- **Evidence**: E-38
- **Links**: `subsystem` ↔ EK-19；`subsystem` ↔ EK-21
- **Value**: B
- **Epistemic**: Fact

## EK-21 `SessionClosed` 是 best-effort，不能作为清理保证

- **Level**: L2
- **Statement**: 接口注释明确"存储不能依赖该方法被调用"，需自带超时回收；SDK 在 `Close` 中用 `context.TODO()` 调用它，无超时、不可取消。
- **Why**: 进程崩溃/网络断开会跳过关闭回调；同时 SDK 也没有为存储关闭准备可取消的 context。因此契约必须双向保守：存储自带回收，SDK 只做"尽力通知"。
- **Evidence**: E-36, E-39
- **Links**: `dependency` ← EK-19；`subsystem` ↔ EK-20
- **Value**: A（可靠性）
- **Epistemic**: Fact

## EK-22 localhost 服务默认开启 DNS rebinding 防护

- **Level**: L2
- **Statement**: 若 `LocalAddrContextKey` 是 loopback 而 `req.Host` 不是 loopback，直接 403；`DisableLocalhostProtection` 可关闭。
- **Why**: 本地 MCP 服务常监听 127.0.0.1；浏览器中的恶意页面可通过 DNS rebinding 让请求看起来来自 localhost。校验 Host 是低成本、有效的边界。
- **Evidence**: E-41
- **Links**: `subsystem` ↔ EK-23；`subsystem` ↔ EK-24；`constraint` → EK-26
- **Value**: A
- **Epistemic**: Fact

## EK-23 请求体上限在读取期强制，覆盖 chunked/HTTP2

- **Level**: L2
- **Statement**: `http.MaxBytesReader` 包裹 body，默认 4 MiB；超限返回 413；负数关闭限制。
- **Why**: 无 Content-Length 的 chunked/HTTP2 请求无法在路由前判断大小；在读取期强制才能防 OOM。
- **Evidence**: E-42
- **Links**: `subsystem` ↔ EK-22；`subsystem` ↔ EK-24
- **Value**: B
- **Epistemic**: Fact

## EK-24 SSE 长流用 30s 注释行保活，且区分"提交前/提交后"

- **Level**: L2
- **Statement**: `StreamKeepAlive` 默认 30s；`subscriptions/listen` 只在 ack 提交响应头后开始保活，其它流首次注释即提交头；保活写失败视为断连。
- **Why**: 中间代理常按空闲超时切断长连接；注释行不计入 SSE 事件，但能续命。提交前不发保活，是为了保留"还能改 HTTP 状态码"的能力。
- **Evidence**: E-43
- **Links**: `subsystem` ↔ EK-23；`subsystem` ↔ EK-25
- **Value**: B
- **Epistemic**: Fact

## EK-25 请求取消传导只对新协议开启，且默认关闭

- **Level**: L2
- **Statement**: `PropagateRequestCancellation=true` 时，新版协议的 handler context 与 HTTP 请求 context 绑定；旧协议（含兼容路径）不受影响。
- **Why**: 新协议下 POST 就是完整请求生命周期，HTTP 断开意味着响应无法送达，取消 handler 是安全的；旧协议可能还有后续 GET/SSE，不能直接取消。
- **Evidence**: E-44
- **Links**: `subsystem` ↔ EK-24；`constraint` → EK-18
- **Value**: B
- **Epistemic**: Observation

## EK-26 Bearer 中间件的检查顺序是"认证→过期→授权"

- **Level**: L2
- **Statement**: 解析 header → verifier → expiration（含 ClockSkew）→ scope；错误码严格区分 401 invalid_token 与 403 insufficient_scope。
- **Why**: 过期令牌应促使客户端换 token（401），而不是申请更多 scope（403）；顺序反了会给客户端错误指令。
- **Evidence**: E-47, E-48
- **Links**: `mechanism` ↔ EK-27；`dependency` → EK-08；`constraint` ← EK-22
- **Value**: A
- **Epistemic**: Observation

## EK-27 token 校验默认 fail-closed（缺失 expiration 直接拒绝）

- **Level**: L2
- **Statement**: `TokenInfo.Expiration` 为零且 `AllowMissingExpiration=false`（默认）时返回 401 `invalid_token`。
- **Why**: 没有过期时间的 token 等价于永久凭证；默认拒绝可以防止"忘记设置过期"变成安全漏洞。
- **Evidence**: E-48
- **Links**: `mechanism` ↔ EK-26；`constraint` ← EK-09
- **Value**: A
- **Epistemic**: Fact

## EK-28 OAuth 能力是分层的，缺口被写进 conformance baseline

- **Level**: L2
- **Statement**: `auth/` 提供 authorization code、client credentials、OIDC login、enterprise handler；`oauthex/` 提供 metadata/DCR/token exchange；但 `conformance/baseline.yml` 明确列出 client-credentials-jwt、enterprise-managed-authorization、DPoP、DPoP nonce、WIF JWT-bearer **未实现**。
- **Why**: OAuth 生态的标准是渐进落地的；与其声称"支持 OAuth"而隐藏缺口，不如用 baseline 把"不跑的用例"显性化，让使用者按需选择。
- **Evidence**: E-49, E-47
- **Links**: `mechanism` ↔ EK-29；`subsystem` ↔ EK-27
- **Value**: A
- **Epistemic**: Observation

## EK-29 `rough_edges.md` 把不可修复的 v1 API 缺陷显性化

- **Level**: L2
- **Statement**: 官方列出 8 类问题（EventStore.Open 多余、Event 不应导出、无效工具名只能 error log、命名不一致、AudioContent 接收者、Roots 字段、默认能力非空、CreateMessageResult 单数），每条给 workaround，并说明"v2 才能改"。
- **Why**: v1 之后不能破坏兼容；把缺陷写成公开清单，比藏在 issue 里更能阻止使用者误用，也为 v2 提供迁移依据。
- **Evidence**: E-50
- **Links**: `mechanism` ↔ EK-28；`subsystem` ↔ EK-30
- **Value**: A（方法论）
- **Epistemic**: Fact

## EK-30 许可证迁移与文件头存在"声明-实现"不一致

- **Level**: L2
- **Statement**: LICENSE 声明从 MIT 迁移到 Apache-2.0（文档 CC-BY-4.0，未同意重许可的 MIT 贡献仍为 MIT）；但 120 个 Go 文件头写 "MIT-style license"，0 个写 "Apache License"，116 个写 "Copyright 2025 The Go MCP SDK Authors"。
- **Why**: 大规模重许可通常先改 LICENSE，再逐文件改头；文件头未同步会让下游合规扫描得出与 LICENSE 不同的结论。
- **Evidence**: E-51, E-52
- **Links**: `subsystem` ↔ EK-29；`mechanism` ↔ EK-11（同为"治理元数据需可审计"）
- **Value**: B（合规）
- **Epistemic**: Fact
