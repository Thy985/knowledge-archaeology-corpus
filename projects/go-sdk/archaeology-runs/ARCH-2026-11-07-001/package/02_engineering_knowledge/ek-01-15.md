# 02.2 Engineering Knowledge · EK-01 ~ EK-15

---

## EK-01 客户端采用"探测优先 + 失败回退"的双协议栈，而不是版本开关

- **Level**: L2
- **Statement**: 当请求版本 ≥2026-07-28 时，`Client.Connect` 先发无状态 `server/discover`；只有收到任何非现代错误（包括不支持、网络错误）才回退到 legacy `initialize`，并把回退版本固定为 2025-11-25。
- **Why**: 新版协议取消了 initialize 作为能力发现入口；如果客户端硬编码走 initialize，会与新版服务端的语义冲突。用"先试新、失败再旧"可以把两条路径都保留，且不需要用户显式选择协议代际。
- **Evidence**: E-22, E-23, E-25
- **Links**: `mechanism` ↔ EK-02；`causal` → EK-04；`contrast` ↔ EK-05
- **Value**: A
- **Epistemic**: Observation（单项目内多路径证据闭合）

## EK-02 `server/discover` 是"无握手的能力查询 RPC"

- **Level**: L2
- **Statement**: `discover` 在服务端返回 transport 可服务的版本列表、服务端 capabilities、instructions；它不建立持久会话，版本不匹配时不记录 `InitializeParams`。
- **Why**: 要让客户端在"还没有会话"时就能知道对方支持什么；这样服务端可以在每次请求上重新判定版本，而不依赖一次握手的结果。
- **Evidence**: E-26, E-27, E-28
- **Links**: `mechanism` ↔ EK-01；`dependency` → EK-03
- **Value**: A
- **Epistemic**: Fact

## EK-03 协议版本能力由 transport 过滤，而不是由 Server 单方面声明

- **Level**: L2
- **Statement**: `Server.Connect` 计算 `ServerSession.supportedVersions = filterSupportedVersions(transport, server.protocolVersions)`；transport 可选实现 `ProtocolVersionSupporter`，未实现则视为支持所有版本。
- **Why**: 同一个 Server 可能挂在不同 transport 上（stdio 与 Streamable HTTP 的能力不同）。把"实际能服务"的版本下沉到 transport，避免 discover 宣告了 transport 做不到的版本。
- **Evidence**: E-28, E-29
- **Links**: `dependency` ← EK-02；`subsystem` ↔ EK-18
- **Value**: B
- **Epistemic**: Observation

## EK-04 旧握手路径"永不拒绝"，而是返回一个可协商版本让客户端自行断开

- **Level**: L2
- **Statement**: `SupportedProtocolVersions` 只能收窄；新版请求被排除版本会收到 `CodeUnsupportedProtocolVersion`，但 legacy initialize 永不报错——若列表里没有可协商版本，就返回 2025-11-25，让客户端意识到无法继续并断开。
- **Why**: 规范要求服务端用"它支持的版本"回应不支持的请求；直接报错会让旧客户端误以为服务不可用。返回一个旧版本可以让客户端按自己的兼容策略决定是否断开。
- **Evidence**: E-07, E-25（`ServerOptions` 注释）
- **Links**: `causal` ← EK-01；`constraint` → EK-05
- **Value**: B
- **Epistemic**: Observation

## EK-05 "无状态"仍创建请求级会话，去掉的是跨请求标识

- **Level**: L2
- **Statement**: `Stateless=true` 时每个 POST 都调用 `connectStreamable` 新建 `ServerSession`，请求结束 `defer session.Close()`；不读/不设 `Mcp-Session-Id`，GET/DELETE 405，server→client 请求立即拒绝。
- **Why**: 协议无状态化要解决的是"水平扩展时无需共享会话存储"，而不是"没有会话对象"。保留请求级 session 可以让 handler/中间件继续使用统一 API，同时把状态生命周期压到单次请求。
- **Evidence**: E-09, E-10, E-13, E-39（Stateless 文档）
- **Links**: `mechanism` ↔ EK-06；`contrast` ↔ EK-07；`mechanism` ↔ EK-10
- **Value**: A
- **Epistemic**: Observation

## EK-06 旧协议请求靠"合成初始化状态"通过 init gate

- **Level**: L2
- **Statement**: `ephemeralConnectOpts` 对旧协议请求伪造 `InitializeParams{ProtocolVersion}`、空 `InitializedParams` 和 `LogLevel="info"`，使没有握手的请求不被 session 初始化检查拒绝。
- **Why**: 无状态路径下没有地方保存握手结果；但下游 handler 仍假设 `InitializeParams` 存在。合成状态是"兼容层"而不是"真实握手"。
- **Evidence**: E-19, E-20
- **Links**: `mechanism` ↔ EK-05；`constraint` → EK-12
- **Value**: B
- **Epistemic**: Fact

## EK-07 有状态会话用 map + 空闲超时 + 并发 POST 计数管理

- **Level**: L2
- **Statement**: 有状态模式把 `sessionInfo` 存入 `h.sessions`；`SessionTimeout>0` 时用 `AfterFunc` 关闭；`startPOST/endPOST` 对并发 POST 计数，最后一个请求结束才重置超时。
- **Why**: 一个会话可能同时有多个 POST；如果每个请求结束都重置计时器，长请求会掩盖空闲；用计数可以只在"真正无在途请求"时开始计时。
- **Evidence**: E-16, E-17
- **Links**: `subsystem` ↔ EK-08；`contrast` ↔ EK-05
- **Value**: B
- **Epistemic**: Observation

## EK-08 会话与 token 用户绑定，防止会话劫持

- **Level**: L2
- **Statement**: 创建会话时复制 `TokenInfo.UserID`；后续请求经 `lookupSession` 比对，不匹配返回 403 `session user mismatch`。
- **Why**: `Mcp-Session-Id` 是可猜测/可泄漏的 bearer 标识；如果只校验 token 合法而不校验"是不是同一个人"，攻击者可用自己的合法 token 接管他人会话。
- **Evidence**: E-15, E-47
- **Links**: `subsystem` ↔ EK-07；`dependency` ← EK-26；`contrast` ↔ EK-09
- **Value**: A
- **Epistemic**: Observation

## EK-09 无状态化使"会话级身份绑定"退化为"请求级 token 校验"

- **Level**: L2
- **Statement**: 无状态模式没有跨请求会话，`lookupSession` 不被调用；身份保证只剩每个请求的 `RequireBearerToken` 校验。
- **Why**: 不是遗漏，而是无状态的必然结果：没有会话对象可绑定。安全强度从"token + 会话绑定"降为"token"，需要部署方用其他机制（短 token、mTLS、请求签名）补偿。
- **Evidence**: E-09, E-15
- **Links**: `contrast` ↔ EK-08；`constraint` → EK-27
- **Value**: A
- **Epistemic**: Observation

## EK-10 `allowsessionsinstateless=1` 是"回退到旧无状态语义"的逃生舱

- **Level**: L2
- **Statement**: 打开该 MCPGODEBUG 后，无状态服务端重新读取 `Mcp-Session-Id`、接受 DELETE（no-op），恢复 1.7.0 之前的行为。
- **Why**: 已有部署可能依赖"无状态但仍带 session header"的行为；直接切换会破坏兼容。用运行时开关而非 API 变更，避免 v1 内的破坏性修改。
- **Evidence**: E-10, E-11, E-50
- **Links**: `mechanism` ↔ EK-11；`mechanism` ↔ EK-05
- **Value**: B
- **Epistemic**: Fact

## EK-11 兼容行为按版本号累积为 MCPGODEBUG 开关，而不是散落分支

- **Level**: L2
- **Statement**: `docs/mcpgodebug.md` 按 1.4.x→1.9.0 逐版本记录开关；默认新行为，旧行为需显式 `MCPGODEBUG=<name>=1`。
- **Why**: 让"兼容"可审计、可退役：每个开关有引入版本和语义，避免代码里出现无法追踪的历史分支。
- **Evidence**: E-50
- **Links**: `mechanism` ↔ EK-10；`subsystem` ↔ EK-30
- **Value**: B

## EK-12 初始化门禁被注释，当前是 fail-open

- **Level**: L2
- **Statement**: `ServerSession.checkInitialized` 的校验逻辑整段被注释，函数恒返回 nil；只有 `initialized` 通知处理会检查"initialize 之前不能 initialized"和"不能重复 initialized"。
- **Why**: 注释给出原因："server tests don't await the initialized notification"（测试不稳定），并留 TODO 建议请求阻塞等待 initialized。也就是说，这是为测试便利牺牲了门禁。
- **Evidence**: E-30, E-31
- **Links**: `contrast` ↔ EK-13；`constraint` ← EK-06
- **Value**: A（安全相关）
- **Epistemic**: Fact

## EK-13 initialized 通知本身是严格校验的

- **Level**: L2
- **Statement**: `initialized` 处理要求 `InitializeParams != nil`，否则报错；重复 initialized 也报错；通过后调用 `InitializedHandler` 并记录 "session initialized"。
- **Why**: 通知是状态机的显式推进点，重复/乱序会破坏后续订阅与通知语义；请求路径的门禁虽然被关，通知路径仍保留最小顺序保证。
- **Evidence**: E-31
- **Links**: `contrast` ↔ EK-12；`causal` → EK-14（新协议不再依赖 initialized）
- **Value**: B
- **Epistemic**: Fact

## EK-14 新协议禁止服务器主动发起 sampling/roots/elicitation

- **Level**: L2
- **Statement**: `assertServerInitiatedRequestAllowed` 在版本 ≥2026-07-28 时对这些方法返回错误，要求改用 `InputRequests`。
- **Why**: 无状态请求/响应模型下，服务器没有"随时向客户端发起请求"的通道；把交互折叠进一次工具调用的多轮结果，才能保持请求边界清晰。
- **Evidence**: E-32, E-33
- **Links**: `mechanism` ↔ EK-15；`causal` ← EK-13
- **Value**: A
- **Epistemic**: Observation

## EK-15 多轮往返用 `InputRequiredResult + InputRequests` 表达

- **Level**: L2
- **Statement**: 工具/提示/资源 handler 可返回 `resultType=input_required` 与 `InputRequests` 映射；客户端补齐后重试原调用。
- **Why**: 让"需要用户输入"成为一次可重放的调用结果，而不是服务器挂起等待；这对无状态、可重试、可水平扩展的部署是必要条件。
- **Evidence**: E-33
- **Links**: `mechanism` ↔ EK-14；`mechanism` ↔ EK-16
- **Value**: A
- **Epistemic**: Fact
