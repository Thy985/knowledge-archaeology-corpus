# 03.1 Knowledge Objects · KO-01 ~ KO-04

---

## KO-01 协议代际迁移：探测优先、无损回退

- **Level**: L3 Pattern
- **Statement**: 当代际协议切换（有状态握手 → 无状态请求）发生时，客户端应先按新协议探测（discover），任何失败都回退旧协议；服务端同时保留两条路径，并用"版本能力过滤"决定 discover 宣告什么。
- **Aggregation rule**: **R2 因果链簇** —— EK-01（探测优先）→ EK-02（discover）→ EK-03（transport 过滤）→ EK-04（旧握手不拒绝）；对照 EK-05（无状态路径）。
- **Cluster**: EK-01, EK-02, EK-03, EK-04, EK-05
- **Evidence**: E-22, E-23, E-26, E-28, E-29
- **解释范围扩大**: 从"客户端连接函数"扩展到"服务端 discover + transport 能力 + 旧握手兼容"三处；解释了为什么同一个 handler 能同时服务两代协议。
- **反例/边界**:
  1. 回退不等于等价：回退后版本固定 2025-11-25，新协议特性（MRTR、`_meta`）全部不可用；
  2. 服务端若把 `SupportedProtocolVersions` 只留 2026-07-28+，旧客户端会在 initialize 收到 2025-11-25 后断开，而非"继续可用"；
  3. 探测失败若由网络错误引起（而非版本不支持），回退仍会发生——可能把瞬时故障误判为协议不兼容。
- **Epistemic**: Validated Pattern（本项目内）；`Cross-project validation pending`
- **Value**: A

## KO-02 无状态化 = 把会话生命周期压到单次请求，而不是消灭会话

- **Level**: L4 Cognitive Model
- **Statement**: 在请求/响应型协议中，"无状态"可实现的形态是**请求级会话对象**：保留统一的 Session API，但把创建/销毁限定在单次请求内，并去掉跨请求标识。
- **Aggregation rule**: **R4 主题簇** —— EK-05（请求级会话）、EK-06（合成初始化状态）、EK-07（有状态对照）、EK-09（身份校验退化）、EK-10（兼容开关）、EK-17（每请求 `_meta`）共同覆盖"无状态到底去掉了什么"。
- **Cluster**: EK-05, EK-06, EK-07, EK-09, EK-10, EK-17
- **Evidence**: E-09, E-10, E-13, E-19, E-20, E-46
- **解释范围扩大**: 同时解释了传输层（每请求 `connectStreamable`）、状态层（合成 `InitializeParams`）、身份层（会话绑定消失）、配置层（`allowsessionsinstateless` 逃生舱）四个现象。
- **反例/边界**:
  1. 请求级会话仍需要 `Server` 对象与 handler 状态；如果 handler 持有跨请求可变状态，无状态只是"名义上的"；
  2. `ephemeralConnectOpts` 的合成状态意味着"没有握手"也能通过初始化检查——调试时不能把 `InitializeParams != nil` 当作"客户端真的初始化过"；
  3. 有状态路径的 `SessionTimeout` / 并发 POST 计数在无状态路径完全不存在，不能把两套生命周期混用。
- **Epistemic**: Validated Pattern（本项目内）；`Cross-project validation pending`
- **Value**: A

## KO-03 会话身份绑定是"传输层不变量"，不是授权中间件的附属品

- **Level**: L3 Pattern
- **Statement**: 只要存在跨请求会话标识，就必须在会话查找点校验"当前 token 用户 == 会话创建用户"；这个检查属于会话层，而不是 token 校验层。
- **Aggregation rule**: **R3 不变量簇** —— EK-08（`lookupSession` 403）、EK-09（无状态退化）、EK-26（Bearer 中间件）、EK-27（fail-closed）汇聚到同一不变量："会话不能被换人使用"。
- **Cluster**: EK-08, EK-09, EK-26, EK-27
- **Evidence**: E-15, E-48
- **解释范围扩大**: 解释了为什么 token 合法仍可能 403（会话 user mismatch），以及为什么无状态模式必须用别的机制补偿（请求签名/mTLS/短 token）。
- **反例/边界**:
  1. 若 `userID == ""`（未启用 auth），绑定检查被跳过——此时"会话劫持"风险回到纯 session ID 猜测；
  2. 无状态模式没有会话，因此不变量不成立；这不是 bug，是模型边界；
  3. 多用户共享同一 token（如服务账号）时，绑定无法区分真实使用者。
- **Epistemic**: Validated Pattern（本项目内）；`Cross-project validation pending`
- **Value**: A

## KO-04 协议版本是"三平面事实"，单一平面校验必然遗漏

- **Level**: L3 Pattern
- **Statement**: 在同时支持多代协议的实现里，版本至少存在于三个平面：HTTP header（旧协议路由）、请求 `_meta`（新协议自描述）、握手结果（会话协商）。任何只校验其中一个平面的实现，都会在另一代协议上失效。
- **Aggregation rule**: **R2 因果链簇** —— EK-17（`_meta`）→ EK-18（header 只校验旧协议）→ EK-03（transport 过滤）→ EK-04（旧握手返回值）。
- **Cluster**: EK-17, EK-18, EK-03, EK-04
- **Evidence**: E-45, E-46, E-28
- **解释范围扩大**: 解释了 `validateProtocolVersion` 为什么只拒绝 `<2026-07-28`、discover 为什么需要单独返回版本列表、旧 initialize 为什么不报错。
- **反例/边界**:
  1. 字符串比较依赖 `YYYY-MM-DD` 格式；若出现非日期版本号，`>=` 比较会失效；
  2. 新协议允许同一连接内多版本，因此"会话协商版本"不再是全局事实；
  3. header 缺失时旧协议被视为"未知版本"，可被当作 initialize 放行——这不是遗漏，而是旧协议的兼容要求。
- **Epistemic**: Validated Pattern（本项目内）；`Cross-project validation pending`
- **Value**: A
