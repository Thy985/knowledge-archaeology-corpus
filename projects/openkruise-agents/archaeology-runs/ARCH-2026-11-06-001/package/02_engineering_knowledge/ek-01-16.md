# Engineering Knowledge — EK-01 ~ EK-16（Project Layer · 状态机与 Reconcile）

> 本层是**推理原材料**，不是"未升维的 KO"。每条 EK 声明 6 类边之一以上；孤立条目须降级或重写（本文件无孤立条目）。
> 证据编号见 `evidence-index.md`。

### EK-01 · 九态生命周期用 Phase 表达"过程"，用 Condition 表达"事实"
- **layer**: L2
- **statement**: Sandbox 用 9 个 Phase 表达生命周期阶段（Pending/Running/Paused/Resuming/Upgrading/Succeeded/Failed/Recycling/Terminating），但"是否真的暂停"由 `SandboxPaused` condition=True 表达。`spec.paused` 只是意图。恢复决策必须读 condition，而不是 Phase/spec——否则会把"意图已改但状态未落"误判为可恢复。
- **evidence**: E-09, E-45
- **links**: `constraint` → EK-37（condition 优先约束 resume 执行）；`mechanism` ↔ EK-16（PrePause 的短路也依赖 condition=True）
- **epistemic**: Fact（S3）
- **value**: A

### EK-02 · Reconcile 在"第一次可能写资源"之前开启 tracing span
- **layer**: L2
- **statement**: 控制器在完成期望门控/限流后、任何写操作前开启 Reconcile span，并把 phase 与全部 condition 的 `status:reason` 记为 before 属性；纯读迭代由 FilteringSpanProcessor 丢弃。这样 trace 只保留"可能改变系统状态"的迭代，且能与随后的 status 写入 span 对比出因果。
- **evidence**: E-10（`sandbox_controller.go:320-355` 注释）
- **links**: `causal` → EK-09（span 的 before 与最终 status 写入构成可对比因果）；`subsystem` ↔ EK-03（都发生在状态计算之前）
- **epistemic**: Fact（S3）
- **value**: B

### EK-03 · 缓存落后时不做"基于陈旧数据的正确计算"，而是短重试
- **layer**: L2
- **statement**: 当 informer 缓存观察到的 resourceVersion 落后于本控制器上次写入时，Reconcile 不继续用缓存计算状态，而是以 `staleCacheRequeueInterval` 重试。原因：陈旧缓存会算出 no-op transition，并把 pending wake 推迟到下一次 informer resync。
- **evidence**: E-11
- **links**: `causal` → EK-04（同属"不要用未观察到的状态做决策"）；`contrast` ↔ EK-04（一个是"等待观察"，一个是"放弃等待并判定超时"）
- **epistemic**: Fact（S3）
- **value**: A（分布式控制器通用反模式）

### EK-04 · ScaleExpectation：创建后等待 informer 观察，超时才放弃
- **layer**: L2
- **statement**: Pod 创建后通过 `ScaleExpectation` 记录期望，只有 informer 观察到对应对象才"满足"；未满足且未超时 → requeue 等待 cache event；超时 → 删除 expectation 继续。这把"API 写成功"与"控制器可见"解耦，避免重复创建。
- **evidence**: E-10（`:274-289`）
- **links**: `mechanism` ↔ EK-03（同一类"观察缺口"处理，策略相反）；`dependency` → EK-09（期望清理在状态写入前完成）
- **epistemic**: Fact（S3）
- **value**: A

### EK-05 · phase 分派是显式 switch，未知 phase 记录并 requeue 而非静默
- **layer**: L2
- **statement**: `switch newStatus.Phase` 为每个已知阶段指定唯一 `Ensure*`；default 分支记录 invalid phase 并 requeue。好处：新增 phase 时必须显式处理，编译期不会"漏掉"；运行时未知值不会造成静默丢事件。
- **evidence**: E-12
- **links**: `subsystem` ↔ EK-06（完成态短路是 switch 前的另一道门）；`constraint` → EK-01（phase 集合是分派的前置定义）
- **epistemic**: Fact（S3）
- **value**: B

### EK-06 · 完成态在 Ensure 之前短路
- **layer**: L2
- **statement**: Succeeded/Failed 在进入 phase 分派前即返回；避免对终态对象继续执行 Ensure\*（可能触发无意义 Pod 操作）。删除中的对象另走 `handleTerminating`，与完成态分流。
- **evidence**: E-14, E-12
- **links**: `constraint` → EK-05（约束分派范围）；`contrast` ↔ EK-08（终态 vs 删除态的处理分歧）
- **epistemic**: Fact（S3）
- **value**: B

### EK-07 · 时间驱动行为集中在 Reconcile 前段的 checkTimers
- **layer**: L2
- **statement**: `checkTimers` 在状态计算之前统一处理 `ShutdownTime`（硬上限，到期删除且不等待 probe）与 `PauseTime`（到期暂停），并用 `calcTimeoutRequeue` 安排下一次唤醒。把"时间"作为与事件同等的一等触发源。
- **evidence**: E-16, E-17, E-18, E-19
- **links**: `causal` → EK-33（PauseTime 到期后的决策仍受 fail-closed 约束）；`subsystem` ↔ EK-34（auto-pause 自己也会写 PauseTime/Schedule）
- **epistemic**: Fact（S3）
- **value**: B

### EK-08 · 暂停期间靠 finalizer 把删除权收归控制器
- **layer**: L2
- **statement**: 首次进入 Paused 流程时添加 `SandboxFinalizer`；暂停期间若用户删除 Sandbox，finalizer 让控制器先清理 Checkpoint/Pod/资源再放行。Resume 完成时 best-effort 移除 finalizer（失败由 `EnsureSandboxTerminated` 兜底）。
- **evidence**: E-21, E-23
- **links**: `causal` → EK-19（Checkpoint 清理是暂停态删除的必要步骤）；`constraint` → EK-06（只对非终态对象加 finalizer）
- **epistemic**: Fact（S3）
- **value**: A

### EK-09 · Ensure 失败也写 status：错误路径不允许丢状态
- **layer**: L2
- **statement**: phase 分派中每个 `Ensure*` 返回错误时，控制器仍调用 `updateSandboxStatus` 持久化本轮计算出的状态（包括 Upgrading 的失败步骤），再返回错误。这样下一次 Reconcile 能从持久化状态续跑，而不是从零重来。
- **evidence**: E-15, E-34
- **links**: `causal` → EK-26（升级失败续跑依赖状态已持久化）；`mechanism` ↔ EK-04（都需要持久化"已观察到/已完成"的进度）
- **epistemic**: Fact（S3）
- **value**: A

### EK-10 · Resume 的容器一致性用镜像引用归一化比较
- **layer**: L1
- **statement**: `isContainersConsistent` 比较 init container 的运行镜像与 `Spec.Images`，并用 `normalizeImageRef` 做 registry 短名归一化（如 `busybox` vs `docker.io/library/busybox`）；只有一致才判定 resume 成功。
- **evidence**: E-24（`common_control.go:353-396`）
- **links**: `dependency` → EK-11（一致性是 markResumeSucceeded 的前置）；`contrast` ↔ EK-21（升级路径用另一套 checkpoint 镜像校验）
- **epistemic**: Fact（S3/S4）
- **value**: B

### EK-11 · Resume 成功无条件置 Resumed=True
- **layer**: L1
- **statement**: `markResumeSucceeded` 不判断 condition 是否存在，直接 `Resumed=True`。原因：升级路径可能没有预置 Resumed condition；若依赖"先有 condition 再更新"，升级恢复会漏标记。
- **evidence**: E-23（`core/util.go:168-200` 注释）
- **links**: `constraint` → EK-25（升级策略决定是否会走到这条路径）；`mechanism` ↔ EK-12（同一函数内同时重置 runtime 状态）
- **epistemic**: Fact（S3）
- **value**: B

### EK-12 · 每次 Resume 都重置 RuntimeInitialized 并触发 CSI 重挂
- **layer**: L2
- **statement**: `markResumeSucceeded` 将 `RuntimeInitialized` 置为 Pending；每次 resume 都让 runtime 重新初始化、CSI 卷重新 mount。这是"恢复不是简单重启容器，而是重建运行时附着状态"的实现表达。
- **evidence**: E-23
- **links**: `causal` → EK-43（唤醒复用 Resume，因而同样触发 runtime 重新初始化）；`mechanism` ↔ EK-23（checkpoint 恢复同样重建 Pod）
- **epistemic**: Fact（S3）
- **value**: A

### EK-13 · Paused 前置门分两段：本地条件初始化 + 外部 Checkpoint 等待
- **layer**: L2
- **statement**: `preparePausedPhase` 先做本地准备（finalizer、condition、PrePause hook），再检查是否存在**与本流程无关**的外部 Checkpoint（例如用户手动创建）；存在则等待。两段分开的原因：外部快照可能正在写同一 Pod，贸然删 Pod 会破坏它。
- **evidence**: E-21, E-22
- **links**: `causal` → EK-14（等待规则由 checkpoint 状态决定）；`constraint` → EK-19（外部 checkpoint 与 pause checkpoint 共用同一 CRD 类型）
- **epistemic**: Fact（S3）
- **value**: A

### EK-14 · 外部 Checkpoint 等待只认"活跃且未超时"的，多个取最新
- **layer**: L1
- **statement**: 只阻塞 phase 为空/Pending/Creating 的 Checkpoint；有删除时间戳、已完成/失败的跳过；创建超过 `checkpointCreationWaitTimeout` 的视为超时忽略。多个活跃时按创建时间（再按 name）取最新作为 blocker。事件只在 reason/message 变化时发，避免事件风暴。
- **evidence**: E-22
- **links**: `constraint` → EK-21（活跃判定与 checkpoint 生命周期同源）；`mechanism` ↔ EK-02（"只保留有信息量的输出"是同一降噪模式）
- **epistemic**: Fact（S3）
- **value**: B

### EK-15 · 已暂停（condition=True）短路，避免重复 PrePause
- **layer**: L2
- **statement**: 若 `Paused` condition 已为 True，`preparePausedPhase` 直接返回 0，不再执行 PrePause。原因：暂停收尾（删 Pod/写状态）可能跨多轮，重复执行 hook 会产生副作用；幂等收尾交给 `EnsureSandboxPaused`。
- **evidence**: E-21
- **links**: `mechanism` ↔ EK-01（condition=True 是"已暂停"的唯一事实）；`causal` → EK-16（at-least-once 契约下的补偿）
- **epistemic**: Fact（S3）
- **value**: A

### EK-16 · PrePause hook 是 at-least-once，不是 exactly-once
- **layer**: L2
- **statement**: hook 命令执行成功后若状态写入失败/进程崩溃，重启后会重放命令。控制器只保证"至少执行一次"，把幂等责任交给用户 hook。这是有意的契约选择（而非缺陷），因为跨进程 exactly-once 需要外部事务。
- **evidence**: E-21（注释）
- **links**: `contrast` ↔ EK-15（短路用于避免**正常路径**重复，但不能防崩溃重放）；`dependency` → EK-09（状态持久化是减少重放窗口的手段）
- **epistemic**: Fact（S3）
- **value**: A（可迁移的 hook 契约知识）
