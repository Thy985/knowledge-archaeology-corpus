# Engineering Knowledge — EK-33 ~ EK-46（Auto-Pause / Pool / Gateway / Quota / Governance）

---

### EK-33 · 自动暂停是 fail-closed 决策：宁可不停，也不误停
- **layer**: L2
- **statement**: `calculatePauseTime` 在以下任一情况返回 nil（不暂停）：无 policy/rule、`ProbeValid=False`、规则三字段缺失、`ThresholdDuration<0`、MessageRegex 编译失败、probe condition 缺失、condition.Status != True、消息不匹配。**注意 `ProbeValid` 是聚合条件——仅 resume 规则出错也会压住 pause 规则**，这是有意保守（"用户还没修好的策略上不 pause"）。
- **evidence**: E-41, E-48
- **links**: `causal` → EK-34（只有算出 pauseTime 才会持久化 resume 决策）；`contrast` ↔ EK-35（pause 侧 fail-closed，resume 侧对解析失败静默）；`constraint` → EK-07（PauseTime 到期只是触发，仍需通过本决策）
- **epistemic**: Fact（S3/S4）
- **value**: A

### EK-34 · 暂停前必须先持久化 resume 决策（Pod 删除后无 probe）
- **layer**: L2
- **statement**: `handleAutoPause` 在 Running 阶段若判定应暂停且 resume 决策尚未持久化，返回 `autoPauseStatusPersistRequeueInterval` 短重排队，**先写 `Status.Schedules[ProbedSchedule].NextResumeTime` 再删 Pod**。原因：暂停后 Pod 不存在，无法再读 probe 时间；若先删 Pod，恢复时间永久丢失。
- **evidence**: E-40, E-42
- **links**: `causal` → EK-38（pause 真正执行时还会改写 ShutdownTime/PauseTime）；`mechanism` ↔ EK-09（"不可逆动作前先落盘"）；`dependency` → EK-37（恢复依赖该 schedule 与 condition）
- **epistemic**: Fact（S3）
- **value**: A（高价值：不可逆动作前的信息保全）

### EK-35 · resume 决策要求 probe 条件为 True，解析失败按"稳态"静默
- **layer**: L2
- **statement**: `calculateResumeTime` 要求配置了 resume rule、Probe 非空、probe condition 存在且 Status=True；`parseProbedScheduleTime` 失败仅以 V(3) 记录并返回 nil，因为 "none" 之类哨兵值是稳态而非故障。pause 侧对无效配置发 Warning，resume 侧对无效时间不打断——两侧错误处理不对称是有意的。
- **evidence**: E-42, E-43
- **links**: `contrast` ↔ EK-33（同一策略对象的两侧采用不同错误策略）；`constraint` → EK-36（解析结果需减 leadTime）
- **epistemic**: Fact（S3）
- **value**: B

### EK-36 · leadTime 默认 5 分钟，负值视为未设
- **layer**: L1
- **statement**: `resumeLeadTime`：LeadTime 为 nil 或 <0 时使用 `defaultResumeLeadTime = 5min`。负 lead 会导致"在要唤醒的任务**之后**才 resume"，因此被显式排除；空 TimeFormat 等价 `unix`。
- **evidence**: E-43
- **links**: `constraint` → EK-35（resumeTime = scheduledAt - leadTime）；`contrast` ↔ EK-14（同为"把无效值归一化到安全默认"）
- **epistemic**: Fact（S3）
- **value**: B

### EK-37 · 只有 Paused condition=True 才执行 resume（意图 ≠ 事实）
- **layer**: L2
- **statement**: `tryResume` 即使到了 resume 时间，也要求 `SandboxPaused condition == True` 才 patch `Spec.Paused=false`；否则仅按 `defaultAutoPauseRequeueInterval` 重试。原因：`Spec.Paused`/`Phase` 只反映意图，若据此恢复，可能在暂停尚未完成时制造竞态或空操作。
- **evidence**: E-45, E-01
- **links**: `constraint` → EK-01（condition 是唯一事实源）；`dependency` → EK-34（schedule 提供时间，condition 提供可执行性）；`contrast` ↔ EK-30（一个等实际状态，一个等外部注解）
- **epistemic**: Fact（S3/S4）
- **value**: A

### EK-38 · 暂停时托管 retention 同步改写 ShutdownTime 与 PauseTime
- **layer**: L1
- **statement**: `pauseSandbox` 在 `Spec.Paused` 已 true 时幂等返回；否则乐观锁 Patch 为 true。若 `resolveRetentionAnnotationOrDefault` 给出托管 retention 且已有 `ShutdownTime`，则用 `PausedShutdownTime(now, retention)` **同时改写 ShutdownTime 与 PauseTime**——保持 PauseTime 对齐，使下次 connect/resume 仍保留 auto-pause 模式。
- **evidence**: E-46, E-20
- **links**: `causal` → EK-07（改写后的时间由 checkTimers 消费）；`mechanism` ↔ EK-44（唤醒时也改写同一组时间字段，方向相反）
- **epistemic**: Fact（S3）
- **value**: B

### EK-39 · 扩缩决策 cron 优先于 capacity，cron 触发即覆盖
- **layer**: L2
- **statement**: `computeDesiredReplicas` 先评估 cron policies；只要有 cron 触发（reason != NoCronTriggered），直接采用 cron 目标副本数，不再走水位算法。这样定时扩缩（如白天扩容/夜间缩容）不会被实时水位抵消。
- **evidence**: E-50, E-54
- **links**: `contrast` ↔ EK-40（capacity 是连续反馈控制，cron 是开环计划）；`constraint` → EK-42（cron 也受 cooldown/边界约束）
- **epistemic**: Fact（S3/S4）
- **value**: A

### EK-40 · 死区 + in-progress guard 抑制扩缩振荡
- **layer**: L2
- **statement**: `computeDesiredReplicas`：`avgAvailable` 落在 [lower, upper] 死区则不变；低于下水位时若 `specReplicas > avgReplicas`（上一次扩容尚未反映到观测）则等待而非再次扩容；高于上水位时若 `specReplicas < avgReplicas` 同理等待收敛。deficit<=0 时强制至少扩 1，防止"低于下水位但算不出缺口"的僵局。
- **evidence**: E-50
- **links**: `causal` → EK-41（死区宽度由 watermark 计算）；`mechanism` ↔ EK-42（都用"等待上一动作收敛"避免振荡）
- **epistemic**: Fact（S3/S4）
- **value**: A

### EK-41 · 百分比 tolerance 锚定 resolved target，而非池规模
- **layer**: L2
- **statement**: `computeWatermarks`：当 target 与 tolerance 都是百分比时先合并再乘 base；混合/绝对值时先把 target 解析成绝对值，再按 **resolved target** 算百分比 tolerance。注释理由：若锚定池规模（base），死区会随池增长而扩大，且 tolerance>target 时下水位被 clamp 到 0 使扩容不可达。
- **evidence**: E-51
- **links**: `constraint` → EK-40（死区边界由此函数决定）；`contrast` ↔ EK-36（同为"避免参数组合产生退化行为"）
- **epistemic**: Fact（S3）
- **value**: A（可迁移的指标计算知识）

### EK-42 · scale-up cooldown 下限耦合 Pod 创建超时 + 安全余量
- **layer**: L2
- **statement**: `resolveScaleUpCooldown` 取 `max(configured, sbxMaxPendingTimeout + 10s)`。原因：扩容刚发出时新 Pod 尚未 Running，若 cooldown 短于 Pod 创建上界，控制器会在观测到新 Pod 前再次扩容，造成超额。cooldown 是与"创建时延"耦合的，而不是独立可调参数。
- **evidence**: E-49, E-53
- **links**: `causal` → EK-40（cooldown 与 in-progress guard 共同防重复扩容）；`dependency` → EK-04（Pod 创建到可见存在时延）
- **epistemic**: Fact（S3/S4）
- **value**: A

### EK-43 · 唤醒复用 Resume 单一实现 + UID 防同名重建误唤醒
- **layer**: L2
- **statement**: `Waker.Wake` 不实现第二套恢复逻辑，而是包装 Sandbox 后调用 `sandboxcr.Sandbox.Resume`（复用 E2B connect 路径的超时/去重/状态语义）。唤醒前用 `SandboxUIDMatches` 校验 registry route 指向的对象 UID；UID 为空/读取失败/已删除/同名重建都返回 false，绝不唤醒。
- **evidence**: E-55, E-56
- **links**: `causal` → EK-12（Resume 会重置 runtime 状态）；`mechanism` ↔ EK-29（都不信任 stale 对象）；`contrast` ↔ EK-17（暂停有 Stop 固定路径，恢复有统一的 Resume 路径）
- **epistemic**: Fact（S3/S4）
- **value**: A

### EK-44 · 唤醒时置 forever ShutdownTime，仅按规则重设 PauseTime
- **layer**: L2
- **statement**: `Wake` 中若沙箱是 auto-pause（`PauseTime != nil`），把 `ShutdownTime` 设为 `now + timeout.ForeverReservePausedSandboxDuration`（远未来常量，具体值定义在本仓库外的 timeout 包），防止陈旧/即将到期的 retained ShutdownTime 删掉刚被流量唤醒的沙箱；仅当 wake rule 的 `PauseTimeout > 0` 才设新 `PauseTime`（并应用 resume timeout floor），否则清空 stale PauseTime，避免 controller 立即再次暂停。never-timeout / shutdown-only 沙箱完全跳过超时设置，避免把 shutdown-only 转成 auto-pause。
- **evidence**: E-56, E-57
- **links**: `contrast` ↔ EK-38（同一组时间字段，暂停时延长、唤醒时置 forever/重设）；`constraint` → EK-07（时间字段由 checkTimers 消费）；`causal` → EK-33（唤醒后若未重设 PauseTime，则不会再触发暂停决策）
- **epistemic**: Fact（S3/S4）
- **value**: A（高价值：事件驱动恢复的边界条件）

### EK-45 · 配额 anti-drift：双向对账 + 仅 leader 写 + grace/Health 防误删
- **layer**: L2
- **statement**: anti-drift 每周期比较"观测到的 live Sandbox"与"配额后端条目"：Phase 1 对每个 live 但缺账/账不对的 Sandbox 执行 `Acquire(Enforce=false)`（补账不拒绝已运行对象）；Phase 2 对后端多余条目，只有 `source.Healthy()` 为真且连续观察超过 `Grace` 才 `Release`。所有写操作前检查 `stillPrimary()`，非 leader 跳过。缓存滞后或 leadership 切换不会造成误释放/重复扣减。
- **evidence**: E-61, E-62, E-63
- **links**: `mechanism` ↔ EK-04（都处理"观察滞后"）；`causal` → EK-40（配额状态影响可扩容量）；`contrast` ↔ EK-02（"只保留有信息量的修复动作"）
- **epistemic**: Fact（S3/S4）
- **value**: A

### EK-46 · 分层依赖与 controller 闭包隔离是架构可执行约束
- **layer**: L2
- **statement**: 项目用 `AGENTS.md` 明文规定 API→Manager→Infra 单向依赖、controller 依赖闭包不得含 servers/manager、`pkg/features` 仅 controller 可用，并把"现有跨层导入"定义为 legacy debt 而非先例。效果是控制面 operator 可独立于数据面服务演进；代价是共享代码必须放在真正中立的包，不能借 utils 隐藏反向依赖。
- **evidence**: E-06, E-07, E-08
- **links**: `constraint` → EK-17（controller 与 manager 各自实现生命周期，不能相互复用）；`contrast` ↔ EK-45（一个用规则隔离演进，一个用对账收敛状态）
- **epistemic**: Fact（文档规则 S3；是否被 CI 强制未验证，见 C-05）
- **value**: A
