## KO-06 · 自动化的安全默认是 fail-closed，且保守范围要覆盖相邻配置

- **layer**: L3 Pattern → L4 Model
- **aggregation_rule**: R3 不变量簇（EK-33, EK-34, EK-35, EK-36 汇聚到"不可判定时不动作"）
- **cluster**: EK-33, EK-34, EK-35, EK-36（4）
- **epistemic**: Validated Pattern（S3/S4）· `Cross-project validation pending`
- **value**: A

### L1 工程事实
- `calculatePauseTime` 在 ProbeValid=False、字段缺失、负阈值、regex 编译失败、condition 缺失/非 True、消息不匹配时一律返回 nil（EK-33；E-41）。
- `ProbeValid` 是聚合条件：仅 resume 规则配置错误也会压住 pause 规则，这是有意扩大保守范围（EK-33 注释；`pkg/autopause/validation.go:162-169`）。
- resume 侧对时间解析失败静默（哨兵值 "none" 是稳态），pause 侧对无效配置发 Warning——错误处理不对称（EK-35；E-42/E-43）。
- leadTime 为负时按默认 5 分钟，避免"在任务之后才唤醒"（EK-36；E-43）。

### L2 工程知识
自动暂停的风险是不对称的：误暂停会中断用户任务、丢状态；不暂停只浪费资源。因此系统把"无法判定"全部归入"不动作"，并让校验条件聚合到策略级——因为用户配置错误往往同时影响 pause/resume，局部放行会制造"半可用"策略。错误处理的不对称（pause 告警、resume 静默）来自"配置错误"与"稳态哨兵值"的语义差异。

### L3 工程模式
**Fail-closed automation with aggregate validation**：默认不动作；不可判定 → 不动作；校验失败 → 聚合到策略级；稳态哨兵值不当作故障。
同类实例：WAF 默认拒绝、K8s admission webhook 失败关闭、自动扩缩在指标缺失时不缩容。

### L4 认知模型
**自动化系统的风险不对称决定了默认方向：误动作的代价通常大于不动作。** 因此"不可判定"必须映射到"保持现状"，而不是"尝试一下"。

### L5 方法论
1. 枚举触发条件的所有未知/缺失/解析失败分支，逐一映射到"不动作"。
2. 把校验聚合到策略级，避免"部分规则有效"造成半自动状态。
3. 区分"错误"与"稳态哨兵值"，前者告警、后者静默。
4. 为保守策略提供可观测字段（condition/reason），让用户知道"为什么没动作"。

### 反例与边界
- 反例 1：安全场景（如检测到入侵必须隔离）误动作代价更低，应 fail-open 执行 → 边界：**资源优化类**自动化适用 fail-closed；安全响应类不适用。
- 反例 2：永远不动作会让自动化"名存实亡"（用户以为在自动暂停，实际从未触发）→ 项目用 ProbeValid condition + Warning 事件暴露原因，部分缓解。
- 反例 3：聚合校验会让一个无关配置错误压住整个策略，降低可用性 → 项目承认这是"保守的代价"，未按规则粒度拆分。

## KO-07 · 反馈控制的稳定性来自死区、进度感知、与执行时延耦合的冷却

- **layer**: L3 Pattern → L4 Model
- **aggregation_rule**: R4 主题簇（EK-39, EK-40, EK-41, EK-42 覆盖 autoscaling 的四个互补维度）
- **cluster**: EK-39, EK-40, EK-41, EK-42（4）
- **epistemic**: Validated Pattern（S3/S4）· `Cross-project validation pending`
- **value**: A

### L1 工程事实
- cron 触发时直接覆盖 capacity 决策（EK-39；E-50）。
- 水位死区 + in-progress guard（specReplicas 与 avgReplicas 比较）+ deficit<=0 强制扩 1（EK-40；E-50）。
- 百分比 tolerance 锚定 resolved target，而非池规模（EK-41；E-51）。
- scale-up cooldown 下限 = Pod 创建超时上界 + 10s（EK-42；E-49）。
- 观测窗口 30s、采样 5s，窗口未热不做决策（E-53）。

### L2 工程知识
扩缩振荡的根因不是"阈值设错"，而是三个时延叠加：指标采样窗口、Pod 创建时延、决策冷却。项目用死区吸收采样噪声，用 in-progress guard 识别"上一动作未收敛"，用 cooldown 下限覆盖创建时延。三者不是独立参数，而是同一控制回路的不同时间尺度。

### L3 工程模式
**Delay-aware feedback control**：控制周期必须大于执行时延；死区吸收噪声；检测"在途动作"避免重复触发；开环计划（cron）优先于闭环反馈。
同类实例：TCP 拥塞控制（RTT 与窗口）、HPA 的 stabilization window、云厂商 autoscaling 的 cooldown。

### L4 认知模型
**控制回路的稳定性不是算法属性，而是"决策节奏与执行节奏匹配"的属性。** 当决策比执行快，系统会对着尚未生效的结果反复决策，产生振荡。

### L5 方法论
1. 先测执行时延（创建/启动/就绪）的上界，再设冷却下限。
2. 设死区，宽度由指标噪声与业务容忍度决定。
3. 记录"在途动作"，在观测到收敛前不重复决策。
4. 开环计划（定时）与闭环反馈冲突时，明确优先级（本项目 cron 优先）。

### 反例与边界
- 反例 1：执行时延远小于决策周期时，cooldown 下限无意义 → 边界：**有显著创建时延**。
- 反例 2：死区过宽会导致容量长期不足（欠载）→ 需要 SLO 约束，不能只追求稳定。
- 反例 3：cron 优先可能覆盖紧急扩容需求（如突发流量）→ 项目选择"计划优先"，属业务取舍，不是普适最优。

## KO-08 · 事件驱动的恢复必须与旧的生命周期边界重新协商

- **layer**: L3 Pattern → L4 Model
- **aggregation_rule**: R1 机制簇（EK-43, EK-44, EK-12, EK-38 共享"恢复即重新进入生命周期"机制）
- **cluster**: EK-43, EK-44, EK-12, EK-38（4）
- **epistemic**: Validated Pattern（S3/S4）· `Cross-project validation pending`
- **value**: A

### L1 工程事实
- 唤醒复用 `sandboxcr.Sandbox.Resume`，不实现第二套恢复逻辑（EK-43；E-56）。
- 唤醒时若为 auto-pause，把 ShutdownTime 置为 now + `ForeverReservePausedSandboxDuration`（远未来），防止旧 retention 立即删除（EK-44；E-56）。
- 仅当 wake rule 的 PauseTimeout>0 才重设 PauseTime，并应用 resume timeout floor；never-timeout/shutdown-only 跳过（EK-44；E-57）。
- 每次 Resume 重置 RuntimeInitialized（EK-12；E-23）。
- 暂停时托管 retention 同时改写 ShutdownTime 与 PauseTime（EK-38；E-46）。

### L2 工程知识
被暂停的沙箱仍保留 `ShutdownTime`（暂停前设定的硬上限）和 `PauseTime`（自动暂停计划）。流量唤醒只改 `Spec.Paused=false` 并不够：旧 ShutdownTime 可能已临近，会在恢复后立刻删除；旧 PauseTime 可能已过期，会让控制器马上再次暂停。因此恢复路径必须**重写这两个未来定时器**，并重新初始化运行时。恢复不是"把 Pod 拉起来"，而是"重新进入生命周期"。

### L3 工程模式
**Resume = re-enter lifecycle**：恢复流程要显式重协商所有"未来会作用于我"的定时器/策略/身份；复用既有 Resume 实现，避免两套恢复语义分叉。
同类实例：云函数冷启动重置 idle timer、K8s Pod 重启后的 probe 重新计窗、OAuth 刷新令牌后重设过期。

### L4 认知模型
**恢复不是一个时间点，而是重新进入一个仍带着旧约束的生命周期。** 旧约束不会因恢复而消失，必须被显式替换或清除，否则恢复会被过去的策略再次杀死。

### L5 方法论
1. 列出恢复后仍生效的定时器/配额/策略（shutdown、pause、lease、token TTL）。
2. 判断哪些会与新意图冲突；冲突项显式重写或清空。
3. 对"永不超时/仅 shutdown"等特殊模式保持原语义，不强行转换。
4. 恢复后重初始化依赖（runtime、CSI、凭据）。

### 反例与边界
- 反例 1：无自动暂停/无硬上限的沙箱，恢复无需重协商 → 边界：**存在生命周期定时器**。
- 反例 2：把 ShutdownTime 置为 100 年是"事实上的永久"，可能掩盖资源泄漏 → 项目用 paused-retention 作为补偿，但仍需外部配额/巡检。
- 反例 3：若用户显式设置的 ShutdownTime 被唤醒覆盖，可能与用户意图冲突 → 项目只在 autoPause 时覆盖，shutdown-only 不动，属有条件适用。

## KO-09 · 架构治理的有效性取决于边界是否可检查，而不是文档是否完整

- **layer**: L3 Pattern（L4 倾向，证据部分）
- **aggregation_rule**: R3 不变量簇（EK-05, EK-06, EK-25, EK-46 汇聚到"边界必须显式且默认安全"）
- **cluster**: EK-05, EK-06, EK-25, EK-46（4）
- **epistemic**: Pattern（project-specific）· 采纳效果未验证 · `Cross-project validation pending`
- **value**: B

### L1 工程事实
- `AGENTS.md` 规定 API→Manager→Infra 单向依赖、controller 闭包隔离、`pkg/features` 仅 controller 可用，并把现有跨层导入定义为 legacy debt（EK-46；E-06/E-07/E-08）。
- 控制器注册集中在 `Deps`，注释说明"新增依赖破坏 compile-time checks，故集中"（E-05；controllers.go:22-65）。
- phase 分派显式、未知 phase requeue（EK-05；E-12）；终态 Ensure 前短路（EK-06；E-14）；升级默认不支持（EK-25；E-33）。
- 仓库**未发现**强制依赖方向的 CI/lint 规则；`docs/proposals/` 目录不存在（C-05）。

### L2 工程知识
项目用"显式枚举 + 集中注册 + 默认不动作"降低架构漂移：新增 phase/控制器必须被显式处理，未知值不会静默通过；默认值选择安全侧。但这些约束大多靠 review 与文档执行，缺少自动检查——这正是"规则存在"与"规则生效"的差距。

### L3 工程模式
**Checkable boundaries**：把分层/依赖/命名/生成文件规则写成可自动执行的检查（import 规则、CI、schema 校验），而不是仅写在 AGENTS.md。
同类实例：ArchUnit、import-linter、Go 的 `internal/` 包、Bazel visibility。

### L4 认知模型
**一个边界的强度等于它的检查强度，而不是它的描述强度。** 没有检查的边界在压力下会退化为"legacy debt"，而文档会把退化合法化。

### L5 方法论
1. 把每条架构规则映射到一种可执行检查（静态分析/CI/测试）。
2. 对无法自动检查的规则，明确 owner 与 review checklist。
3. 记录"legacy debt"清单并设收敛目标，避免其成为新工作的先例。
4. 默认值/枚举分支采用安全侧，未知输入显式失败。

### 反例与边界（本条尤其重要）
- 反例 1（支持而非削弱）：仓库确实存在 `Deps` 集中注册与显式 phase switch，说明"显式化"部分已落地。
- 反例 2（削弱）：`docs/proposals/` 不存在、无依赖 lint → 规则的可检查性未证实，因此 L3 只能算 **Pattern（采纳未验证）**，不能升为"有效治理模型"。
- 反例 3：小团队/早期项目用文档 + review 足够，引入 lint 成本过高 → 边界：**规模/协作人数**决定检查投入。
- 结论：KO-09 保留在 L3，L4 的表述作为**倾向性模型**而非已验证原则；不进入 L4 正式层。
