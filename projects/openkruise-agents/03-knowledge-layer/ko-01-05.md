# Knowledge Layer — KO-01 ~ KO-05（Generalized Knowledge）

> 升维规则：每条 KO 必须能回溯到 EK 簇（`aggregation_rule`），并给出 L1→L5 的完整链。单项目证据 → 一律标 `Cross-project validation pending`，不写成通用定律。
> 反例攻击见 `06_validation/counterexamples.md`。

## KO-01 · 不可逆动作前，先把"如何恢复"持久化

- **layer**: L3 Pattern（L4 倾向）
- **aggregation_rule**: R2 因果链簇（EK-33 → EK-34 → EK-38 → EK-07，辅以 EK-01/EK-37 的 condition 约束）
- **cluster**: EK-33, EK-34, EK-38, EK-07, EK-01, EK-37（6）
- **epistemic**: Validated Pattern（本项目 S3/S4）· `Cross-project validation pending`
- **value**: A

### L1 工程事实
- 自动暂停在 Running 阶段算出 pauseTime 后，若 resume 决策尚未持久化，先返回 1s 重排队，把 `NextResumeTime` 写入 `Status.Schedules`，下一轮才删 Pod（EK-34；E-40）。
- Pod 删除后 probe 不再可用，无法重新计算 resume 时间（EK-34 注释）。
- 暂停执行时若存在托管 retention，同时改写 `ShutdownTime` 与 `PauseTime`（EK-38；E-46）。
- Ensure 失败也写 status，使升级失败步骤可续跑（EK-09；E-15）。

### L2 工程知识
暂停的恢复依据有两类：(a) probe 实时值，(b) 已持久化的 schedule。删 Pod 会使 (a) 永久消失，所以系统把决策结果转存为 (b)，把"可恢复性"从运行时状态变成持久化状态。这不是性能优化，而是**信息保全**：不可逆动作会摧毁它自身所需的输入。

### L3 工程模式
**Persist-before-irreversible**：在执行删除/替换/释放/驱逐等不可逆动作前，先检查"恢复或补偿所需的输入"是否已落到可读存储；若没有，先持久化再执行。
同类实例：数据库 WAL（写前日志）、K8s 删除前写 deletionTimestamp、任务队列的 checkpoint、事务的 undo log。

### L4 认知模型
**恢复信息的可得性与动作的可逆性成反比。** 动作越不可逆，恢复所需的输入越可能在动作后消失；因此恢复依据必须在动作前转存，而不能依赖"事后重新观测"。

### L5 方法论
1. 列出每个不可逆动作的"恢复输入"（时间、配置、映射、凭据、进度）。
2. 判断这些输入在动作后是否仍可观测；不可观测的必须前置持久化。
3. 持久化写入与不可逆动作分两轮执行（先写后删），并用短重排队保证顺序。
4. 失败路径也要写状态，保证"部分完成"可续跑。

### 反例与边界
- 反例 1：若恢复输入可从外部系统廉价重建（如从模板重新生成），前置持久化是过度设计 → 边界：**重建成本 > 持久化成本**时才成立。
- 反例 2：若持久化本身失败且动作必须执行（如安全驱逐），系统需要降级策略而非无限重试 → OpenKruise 的 `handleShutdownTimeout` 就不等 probe，说明"硬上限"优先于"保全恢复信号"。
- 因此 KO-01 不是绝对原则，而是**默认优先级**：能保全则保全，硬约束（安全/资源上限）可覆盖。

## KO-02 · "类型/文档声明存在"不等于"运行时可达"

- **layer**: L3 Pattern（L4 倾向）
- **aggregation_rule**: R1 机制簇（EK-17, EK-18, EK-19, EK-27 共享"类型-实现-可达性"机制）
- **cluster**: EK-17, EK-18, EK-19, EK-27（4）
- **epistemic**: Validated Pattern（S3，grep/调用图可复现）· `Cross-project validation pending`
- **value**: A

### L1 工程事实
- `PauseStrategyType` 枚举 `Stop;Hibernate`，`HibernateStrategy` 也有定义；但 `pkg/` 生产代码对 `PauseStrategy.Type` 无任何读取/分支（EK-18；E-28）。
- `EnsureSandboxPaused` 固定调用 `ensureStopPaused`；`getControl` 忽略 Pod 参数，只注册了 commonControl（EK-17；E-24/E-27）。
- `ensureCheckpointPaused` 实现完整，唯一调用者是单测（EK-19；E-26）。
- 相反，升级路径的 `EnsureCheckpointForUpgrade` 第一行就按 `UpgradePolicy.Type` 分支（EK-27；E-35）。
- revision hash 的 legacy 兼容（EK-32）说明项目确实在意"旧对象不被误判"，但这属于版本兼容，不是能力可达性，故不并入本条。
- CHANGELOG 写 `Stop / Snapshot / CloudDisk` 三值，代码 enum 只有两值，且 `CloudDisk` 全仓无命中（E-67）。

### L2 工程知识
同一个仓库里，**"类型分支"是否真的被执行**取决于调用方是否把该字段传到实现，而不仅仅是类型是否存在。暂停路径的 `EnsureSandboxPaused` 没有接收/读取策略，于是类型定义变成"装饰"；升级路径在入口处判断策略，于是类型真正生效。差异的根因是"策略字段是否进入控制流"，不是"类型是否定义"。

### L3 工程模式
**Reachability-first capability audit**：评估一个能力是否存在，构造 `入口 → 分派 → 实现` 的调用链并检查分支条件；不以类型定义、文档、CHANGELOG、单元测试的存在作为能力证据。
同类实例：feature flag 定义了但未在代码中判断；API 字段序列化但后端忽略；SDK 方法存在但服务端未实现。

### L4 认知模型
**"存在性"有三个层次：声明存在（类型/文档）、实现存在（函数体）、运行可达（调用链 + 条件分支）。只有第三层对用户成立。** 三者之间的缺口不会自动弥合，且单测可能只验证第二层。

### L5 方法论
1. 对每个宣称的能力，画出调用链（grep 调用者，而非只 grep 定义）。
2. 检查链上的每个条件分支是否读取了对应配置/字段。
3. 区分"测试调用"与"生产调用"；测试覆盖不算可达性证据。
4. 把"声明 vs 实现 vs 可达"三列写进能力清单，缺口单列为 Candidate，不写成能力。

### 反例与边界
- 反例 1：某些能力故意保留为"未来扩展点"（如 Hibernate 可能是 roadmap 项）→ 这仍是缺口，只是**有意**缺口；应标 Candidate 并注明 roadmap 证据，而不是判定为 bug。
- 反例 2：若能力由外部组件（非本仓库）消费字段，本仓库 grep 不到分支不代表不可达 → 边界：需检查 CRD 消费者/其他仓库；本轮仅覆盖本仓库。
- 结论：KO-02 是**审计方法**，不是"类型定义无用"的断言。

## KO-03 · 控制器的"状态"是意图 + 观察，观察缺口必须被显式建模

- **layer**: L3 Pattern → L4 Model
- **aggregation_rule**: R1 机制簇（EK-03, EK-04, EK-09, EK-29, EK-45 共享"不信任本地/缓存状态"机制）
- **cluster**: EK-03, EK-04, EK-09, EK-29, EK-45（5）
- **epistemic**: Validated Pattern（S3/S4）· `Cross-project validation pending`
- **value**: A

### L1 工程事实
- 缓存 resourceVersion 落后时，不基于缓存算状态，改用短重试（EK-03；E-11）。
- 创建 Pod 后用 ScaleExpectation 等 informer 观察，超时才删除期望（EK-04；E-10）。
- Ensure 失败也持久化 status（EK-09；E-15）。
- Recreate 升级完成后重新 Get Pod，因旧对象已 stale（EK-29；E-36）。
- 配额对账只在 leader 上写，且 Phase 2 需 Health + grace（EK-45；E-61~63）。

### L2 工程知识
控制器同时持有三种"状态"：期望（我想让世界变成什么）、本地缓存（我以为世界是什么）、真实世界（API server 中的对象）。三者不同步时，基于本地缓存的"正确计算"会产生**伪正确**结果（no-op transition、stale Pod、重复扩容、误释放配额）。项目的应对不是"让缓存更快"，而是把不同步显式建模为可等待/可重试/可从观测重建的状态。

### L3 工程模式
**Intent-Observation Reconciliation**：把意图与观察分开存储；每次决策前检查观察是否满足（expectation/version/warm-up）；不满足时选择"等待观察"或"从观测重建"，绝不基于本地推断继续推进。
同类实例：Kubernetes controller 的 expectations、数据库的 read-your-writes 一致性、分布式锁的 lease 观察。

### L4 认知模型
**分布式控制器的有效状态 = 意图 ∩ 观察；交集为空时，任何"计算"都是猜测。** 系统的正确性不取决于算法多聪明，而取决于它是否承认"我还不知道"。

### L5 方法论
1. 每次写后记录期望，并把"观察到"作为独立事件。
2. 为观察缺口设超时；超时后不是"假设成功"，而是重新以观测状态重建。
3. 删除/替换对象后丢弃本地引用，重新 Get。
4. 对账类逻辑只在单一 leader 上执行写，且用 grace 吸收滞后。

### 反例与边界
- 反例 1：强一致存储（如单机 etcd 读）不需要 expectation，直接读即可 → 边界：**存在缓存/异步传播**时才需要。
- 反例 2：纯只读控制器无需写后观察 → 边界：仅"写后立即读"场景。
- 反例 3：`ScaleExpectation` 超时后删除期望继续创建，可能造成重复 Pod → 项目接受该风险（幂等由 Pod 模板/名字约束），说明"等待"不是无限期的。

## KO-04 · 快照的价值在"可重建"，不在"可回滚"

- **layer**: L3 Pattern → L4 Model
- **aggregation_rule**: R2 因果链簇（EK-13 → EK-14 → EK-21 → EK-20 → EK-23 → EK-12）
- **cluster**: EK-13, EK-14, EK-21, EK-20, EK-23, EK-12（6）
- **epistemic**: Validated Pattern（partial；应用已确认、写入路径未确认，见 C-04）· `Cross-project validation pending`
- **value**: A

### L1 工程事实
- Checkpoint status 定义 `PodTemplateDelta`；resume 时 `ApplyPodTemplateDelta` 有生产调用（best-effort，失败继续）（EK-23；`pod_control.go:170-172`）。
- 但 `BuildPodTemplateDelta` 无生产调用，delta 由谁写入本仓库未确认（C-04）——因此"快照保存差异"目前只有读取侧证据，写入侧是 Hypothesis。
- Checkpoint 内容映射：dump 内容（filesystem/memory）与 podInfo 互斥；无 dump 内容时只存 podInfo（EK-20；E-29）。
- 快照前做镜像漂移校验，不一致则阻断删 Pod（EK-21；E-30/E-32）。
- 每次 Resume 重置 RuntimeInitialized，触发 runtime 重新初始化与 CSI 重挂（EK-12；E-23）。
- 外部 Checkpoint 未完成时，暂停流程等待（EK-13/EK-14；E-21/E-22）。

### L2 工程知识
如果只保存文件系统，恢复后的 Pod 可能缺少暂停时注入的环境、卷挂载、sidecar 状态；如果只保存 Pod 模板，又丢失运行时的临时差异。项目用"基础模板 + delta patch"表达重建精度，并在恢复后重新初始化 runtime，把"快照"定义为**重建所需的最小充分信息**，而不是"某个时刻的完整镜像"。

### L3 工程模式
**Reconstructable Snapshot**：快照 = 数据 + 重建补丁 + 恢复后初始化步骤。三者缺一，恢复就会漂移。
同类实例：容器镜像（层 + 配置）、IaC 的 desired state + drift patch、数据库备份 + WAL replay。

### L4 认知模型
**恢复保真度 = 快照覆盖度 × 重建精度 × 初始化完整性。** 只提高其中一项（如只备份更多数据）不会线性提高保真度；短板决定结果。

### L5 方法论
1. 定义"恢复后必须一致"的维度（数据、配置、身份、网络、运行时）。
2. 为每个维度选择载体：数据快照 / 模板 patch / 恢复后重建。
3. 快照前做漂移校验，拒绝在已漂移的对象上快照。
4. 恢复后显式重初始化（runtime、CSI、凭据），不要假设随 Pod 启动自动完成。

### 反例与边界
- 反例 1：无状态服务只需镜像，快照是过度设计 → 边界：**有运行时可变状态**。
- 反例 2：若 delta patch 与模板版本不兼容（模板已滚动），恢复可能失败 → 项目用 revision/ownerReference 约束，但仍存在跨版本风险（C-04）。
- 反例 3：memory checkpoint 可能包含不可序列化的 GPU/设备状态 → 项目把 gpuMemory 单列，说明覆盖度是分级的。

## KO-05 · 生命周期 hook 是"至少一次"，幂等责任在调用方

- **layer**: L3 Pattern → L4 Model
- **aggregation_rule**: R3 不变量簇（EK-15, EK-16, EK-31, EK-24 汇聚到"hook 不可假定只执行一次"）
- **cluster**: EK-15, EK-16, EK-31, EK-24（4）
- **epistemic**: Validated Pattern（S3/S4）· `Cross-project validation pending`
- **value**: A

### L1 工程事实
- PrePause hook 执行成功后若状态写入失败/崩溃，重启会重放命令；注释明确 at-least-once（EK-16；E-21）。
- 已暂停（condition=True）时短路，不再执行 PrePause，避免正常路径重复（EK-15；E-21）。
- PreUpgrade 失败只记录 reason、不返回 error；PrePause 失败则重试到终态（EK-31；E-34/E-21）。
- Resume 收尾先重置 probe 状态再移除 finalizer（EK-24；E-23）。

### L2 工程知识
跨进程的 exactly-once 需要外部事务/去重表；控制器只有"执行 → 写状态"两步，中间崩溃无法原子化。因此系统选择 at-least-once，并把"短路"只用于正常路径的去重，而不是承诺 exactly-once。hook 的副作用（如通知、清理）必须由用户实现幂等。

### L3 工程模式
**At-least-once hook + idempotent side effects**：系统保证"至少调用一次"，调用方保证"重复调用安全"；文档显式声明语义，不用短路伪装 exactly-once。
同类实例：K8s lifecycle hooks、消息队列 at-least-once 投递、CI 的 retry。

### L4 认知模型
**跨进程的"只执行一次"不可得，能保证的是"至少一次"；因此副作用设计必须把重复当作常态。** 幂等不是优化，是分布式语义的前提。

### L5 方法论
1. 在 API 文档中明确 hook 的执行次数语义（at-least-once / at-most-once）。
2. 为 hook 提供幂等键（sandbox UID + phase + revision）。
3. 正常路径用状态短路去重；崩溃路径靠幂等兜底。
4. 对"不可幂等"的操作（如扣款）要求外部去重，不放进 hook。

### 反例与边界
- 反例 1：若 hook 只读、无副作用，重复执行无害，无需幂等 → 边界：**有副作用**。
- 反例 2：若系统引入持久化 job + 去重表，可实现接近 exactly-once → 边界：需要额外存储与协调，OpenKruise 未采用。
- 反例 3：短路条件本身可能因状态写入延迟而失效（condition 未落盘），此时仍会重放 → 说明短路只能降低概率，不能消除。
