# Engineering Knowledge — EK-17 ~ EK-32（Pause / Checkpoint / Upgrade）

---

### EK-17 · 当前 Pause 实现只有 Stop 一种，且是唯一控制实现
- **layer**: L2
- **statement**: `EnsureSandboxPaused` 的注释与实现都只调用 `ensureStopPaused`；`getControl` 忽略 Pod 参数恒返回 `controls["common"]`，而 `controls` 只注册了 `NewCommonControl`。因此无论 `spec.pauseStrategy.type` 写什么，暂停行为都是"删 Pod（grace 5s）"。
- **evidence**: E-24, E-27
- **links**: `causal` → EK-18（策略类型与实际行为脱节）；`contrast` ↔ EK-19（另有完整但未接线的 checkpoint 实现）；`subsystem` ↔ EK-25（升级路径有独立的 checkpoint 实现）
- **epistemic**: Fact（S3，grep 可复现）
- **value**: A

### EK-18 · Hibernate 类型存在但无运行时消费方（类型-实现缺口）
- **layer**: L1
- **statement**: `PauseStrategyHibernate` 只出现在 API 类型定义、deepcopy 与 `sandboxset/revision_test.go`；`pkg/` 生产代码没有任何读取 `PauseStrategy.Type` 并分支的地方。`PauseStrategy` 仅被透传复制（revision、pool materialize、clone）。→ API 声明了一种能力，运行时未实现。
- **evidence**: E-28, E-67
- **links**: `constraint` → EK-17（策略值无法改变唯一实现）；`causal` → EK-19（缺失的消费方正是那段未接线实现）
- **epistemic**: Fact（S3）
- **value**: A

### EK-19 · Checkpoint-based pause 实现完整但不可达（可达性 ≠ 存在性）
- **layer**: L2
- **statement**: `ensureCheckpointPaused` 语义完整（先 `AssumePodCheckpointed` 做镜像校验并驱动 Checkpoint CR，成功后委托 `ensureStopPaused` 并标记 SnapshotPauseSucceed），但**生产代码零调用**，唯一调用者是 `core/util_test.go:1099`。→ 单测通过不代表用户可达；判断能力是否存在必须查调用图，而不是查函数是否存在。
- **evidence**: E-26
- **links**: `contrast` ↔ EK-17（同一问题的两个实现：可达的 Stop vs 不可达的 Checkpoint）；`dependency` → EK-21（若接线，依赖 checkpoint 生命周期正确）
- **epistemic**: Fact（S3/S4：可达性为 Fact；"未来会接线"属 Hypothesis，见 C-01）
- **value**: A

### EK-20 · Checkpoint 内容映射：dump 内容与 podInfo 互斥
- **layer**: L1
- **statement**: `checkpointContentsForPause` 只把 Sandbox 的 `filesystem`/`memory` 映射到 Checkpoint 常量；若没有请求任何 dump 内容，返回 `[]string{podInfo}`；注释明确 dump 内容**绝不与 podInfo 并用**，因为 dump 已自带重建 `PodTemplateDelta` 所需的 pod 信息。
- **evidence**: E-29
- **links**: `constraint` → EK-23（podInfo/dump 决定恢复时是否需要模板补丁）；`mechanism` ↔ EK-22（内容决定 label）
- **epistemic**: Fact（S3）
- **value**: B

### EK-21 · Checkpoint 用 reason 白名单 + 镜像漂移阻断
- **layer**: L2
- **statement**: `AssumePodCheckpointed` 只在 reason ∈ {"", Pending, CheckpointCreating, ImageChanged, CheckpointFailed} 时继续；当 `ValidateImages` 开启且运行镜像与 Sandbox 模板不一致时，置 reason=ImageChanged、发 Warning 事件并返回 true **阻断删 Pod**。这样避免在镜像已漂移的 Pod 上做快照，恢复后得到错误环境。
- **evidence**: E-30, E-32
- **links**: `causal` → EK-17（阻断保证 Stop 前的快照有效）；`mechanism` ↔ EK-10（镜像比较的另一种实现：同名容器 + sidecar init）
- **epistemic**: Fact（S3/S4）
- **value**: A

### EK-22 · Checkpoint label 双代兼容：新内容派生优先，legacy 回退
- **layer**: L1
- **statement**: `ensureCheckpointCR` 先用内容派生 label（如 `filesystem-memory`）查找，找不到再按 v0.5.22 的 legacy label 查找。用于控制器滚动升级期间新旧版本共存：旧版本创建的 Checkpoint 不会被新版本误判为不存在而重复创建。
- **evidence**: E-31
- **links**: `mechanism` ↔ EK-25（升级兼容的另一种形态：版本共存）；`constraint` → EK-20（label 由内容集合决定）
- **epistemic**: Fact（S3）
- **value**: B

### EK-23 · Checkpoint 恢复会应用 PodTemplateDelta，但其写入路径在本仓库未确认
- **layer**: L2
- **statement**: Checkpoint status **定义** `PodTemplateDelta`（running Pod 与"模板 + runtime 注入生成的基础 Pod"之间的 Strategic Merge Patch）；resume 创建 Pod 时 `ApplyPodTemplateDelta` 会被调用，属 best-effort（解析失败仅记日志 + Warning 事件，继续用新生成的 Pod spec）。但 `BuildPodTemplateDelta` 在本仓库**无生产调用**（仅 `utils_test.go`），delta 的写入方未确认。
- **evidence**: `api/v1alpha1/checkpoint_types.go:180-186`；`pkg/controller/sandbox/core/pod_control.go:170-172`；`pkg/controller/checkpoint/utils.go:171/213`（Build 无生产调用）
- **links**: `causal` → EK-12（恢复后 runtime 需重新初始化）；`contrast` ↔ EK-28（升级 CheckpointRestore 只保 filesystem，不用 delta 的全部内容）；`constraint` → EK-15（应用失败不阻断创建）
- **epistemic**: Fact（字段与读取/应用 S3）；**写入路径 Hypothesis**（C-04）
- **value**: A

### EK-24 · Resume 收尾先清 probe 状态再移除 finalizer
- **layer**: L2
- **statement**: `finalizeResumePhase` 顺序为：移除 Paused condition → `resetProbeDrivenState`（清空 probe 驱动的 schedule/条件残留）→ 移除 finalizer（失败仅记日志，由 `EnsureSandboxTerminated` 兜底）。清 probe 状态在 finalizer 之前，保证下一轮暂停周期不继承上一周期的判定。
- **evidence**: E-23, E-48
- **links**: `causal` → EK-33（下一轮暂停决策从干净状态开始）；`mechanism` ↔ EK-15（都是"避免继承旧状态"）
- **epistemic**: Fact（S3）
- **value**: B

### EK-25 · 升级策略空值 = 不支持升级（默认不动作）
- **layer**: L2
- **statement**: `SandboxUpgradePolicy.Type` 为空时 `EnsureSandboxUpgraded` 不做任何替换；只有显式 `Recreate` 或 `CheckpointRestore` 才进入状态机。默认值选择"安全"而非"自动"，避免模板变更意外触发 Pod 重建。
- **evidence**: E-33, E-34
- **links**: `constraint` → EK-26（决定状态机是否启动）；`contrast` ↔ EK-17（暂停有默认行为，升级没有）
- **epistemic**: Fact（S3）
- **value**: A

### EK-26 · 升级是 reason 驱动的多阶段状态机，失败持久化后可续跑
- **layer**: L2
- **statement**: 升级按 `PreUpgrade → Checkpointing → UpgradePod → PostUpgrade → Resuming → ResumeSucceed` 推进，每一阶段的成功/失败都写入 Upgrading condition 的 reason；失败不返回致命错误而是持久化 reason，下一轮从该步骤继续（`SandboxUpgradeResumeFromFailedStepGate` 默认 true）。这使升级对控制器重启/瞬时失败具备恢复性。
- **evidence**: E-34, E-38, E-09
- **links**: `causal` → EK-09（状态持久化是续跑前提）；`mechanism` ↔ EK-45（"从观测到的当前状态继续修复"的同类思想）；`constraint` → EK-25
- **epistemic**: Fact（S3/S4）
- **value**: A

### EK-27 · 非 CheckpointRestore 升级在 Checkpointing 步短路为 done
- **layer**: L1
- **statement**: `EnsureCheckpointForUpgrade` 首先判断 `UpgradePolicy.Type != CheckpointRestore`，是则直接返回 `(true,"",nil)`。状态机仍会经过 Checkpointing 阶段，但该阶段立即完成，避免 Recreate 升级被无意义地阻塞在快照等待。
- **evidence**: E-35
- **links**: `causal` → EK-28（只有 CheckpointRestore 才真正建快照）；`contrast` ↔ EK-17（"类型决定是否执行"在升级路径是实现的，在暂停路径不是）
- **epistemic**: Fact（S3）
- **value**: B

### EK-28 · CheckpointRestore 升级只保留 filesystem（可写层）
- **layer**: L2
- **statement**: CheckpointRestore 的 checkpoint 内容固定为 `[filesystem]`；它保留镜像不变的容器的可写层，不保留 memory/GPU memory。因此它不是"整机热迁移"，而是"保留磁盘增量、重启进程"。
- **evidence**: E-35, E-33（API 注释）
- **links**: `contrast` ↔ EK-23（pause checkpoint 可含 memory/podInfo，升级 checkpoint 只含 filesystem）；`causal` → EK-29（恢复后仍要重建 Pod）
- **epistemic**: Fact（S3）
- **value**: A

### EK-29 · Recreate 升级完成后必须重新 Get Pod（旧对象已 stale）
- **layer**: L1
- **statement**: `performRecreateUpgrade` 删除/替换 Pod 后，完成时重新 `Get` 新 Pod 替换内存对象；注释明确旧对象已删除并被替换，继续使用会读到 stale 状态。这是控制器里"删除+重建"类操作的通用陷阱。
- **evidence**: E-36
- **links**: `causal` → EK-11（后续 Resumed 标记依赖新 Pod 状态）；`mechanism` ↔ EK-04（都不信任本地旧对象）
- **epistemic**: Fact（S3）
- **value**: B

### EK-30 · ResumeSucceed 用 trigger 注解区分"放弃升级"与"等待模板 patch"
- **layer**: L2
- **statement**: 升级进入 Resuming 后，若 `AnnotationUpgradeResumeTrigger != True` 且 `newStatus.UpdateRevision == box.Status.UpdateRevision`，判定"模板 patch 前 trigger 注解被移除 → 放弃升级"，移除 Upgrading condition 回 Running；否则继续等模板 patch。避免用户取消升级后控制器无限等待。
- **evidence**: E-37
- **links**: `constraint` → EK-26（状态机的出口条件）；`contrast` ↔ EK-37（等待"实际状态" vs 等待"外部注解"）
- **epistemic**: Fact（S3）
- **value**: B

### EK-31 · 生命周期 hook 有明确的失败语义分层
- **layer**: L2
- **statement**: PreUpgrade 失败置 `PreUpgradeFailed` 但**不返回 error**（升级流程继续进入 Checkpointing，是否真正升级由后续步骤决定）；PrePause 失败则按 hook requeue 重试直到终态。差异来自"失败是否阻塞不可逆动作"：暂停会删 Pod，必须先确保 hook 完成；升级的 PreUpgrade 失败可以先记录再让策略决定。
- **evidence**: E-21, E-34
- **links**: `contrast` ↔ EK-16（一个是重试到终态，一个是记录后继续）；`causal` → EK-26（reason 持久化）
- **epistemic**: Fact（S3）
- **value**: A

### EK-32 · SandboxSet revision hash 保留 legacy 算法以兼容滚动升级
- **layer**: L2
- **statement**: 新 revision hash 对完整 `SandboxTemplateSpec` 做 FNV-32；legacy 算法只对 `spec.template` 做 hash，注释明确**不包含** `VolumeClaimTemplates`/`PersistentContents`/`Runtimes`/`PauseStrategy`/`Probes`/`AutoPausePolicy`。控制器在升级后仍识别旧 hash，避免把已存在的 Sandbox 误判为"模板已变更"而触发升级。
- **evidence**: `pkg/controller/sandboxset/revision.go:85-140`
- **links**: `mechanism` ↔ EK-22（都是"新旧格式并存"的兼容机制）；`constraint` → EK-25（hash 判定决定是否进入升级）
- **epistemic**: Fact（S3）
- **value**: A（版本兼容的通用工程知识）
